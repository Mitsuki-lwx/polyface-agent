# Design

## Context

证据见 `proposal.md`（30%~33% 逐字重合、字数倒挂、格式项缺失）。
关键约束：Python 侧负责生成与质检；Java 侧编排；既有质检已有一套可复算的检查框架
（`app/pipeline/quality*.py` 那一族），本 change 应**复用**它而不是另起一套。

## Goals / Non-Goals

**Goals**：让"多平台"产出真正分化，且差异**可算**（≤10% 重合、篇幅不倒挂、格式必备项）。

**Non-Goals**

- 不追求"像人写的"这类无法判定的目标 ✗
- 不改平台 DNA / 模板库的既有语义
- 不为了去重而牺牲真话：**同一事实可以重复**，重复的必须是**表达**而不是事实 ✗

## Decisions

### D1：去重靠"已说过的句子"传递，而不是靠阈值猜

生成第 N 篇时，把前 N-1 篇的**句子清单**（截断到预算）作为"这些已经用过的表达"交给模型，
并要求换说法。**检测**则独立于生成：用同一套切句规则算重合率 ✓（生成与检测共用一份实现，
避免"生成侧以为改了、检测侧仍判重" ✗）。

### D2：篇幅用**窗口**而非单一目标值

每个平台一个 `(min, max)` 字数窗口；prompt 里给窗口，质检按窗口判。
"不倒挂"是一条**跨篇**约束，在批次结束时检查 ✓。

### D3：格式必备项写成**可数**的规则

- 话题标签：正则 `#[^\s#]{1,20}` 计数 ≥5
- 小标题：公众号的 `##`/加粗行/独立成行短句计数 ≥3
- 知乎结论先行：首句长度 ≤60 且不含"首先/其实"这类铺垫词

被否：让模型自评"是否符合平台" ✗ —— 不可复算，且上一次已经证明它自评会失真 ✓。

### D4：既有成稿可离线复算

检查函数接受"成稿文本"而非"生成上下文"，因此既能进管线，也能对历史成稿跑 ✓
（验收里有一条就是用上次那三篇复算出 30/33/33 ✓）。

## Risks / Trade-offs

- [过度去重的代价] 金句被删光、三篇都变平庸 ✗ → 只要求**表达**不重复，**事实与数据**必须保留；
  重合阈值定在 10% 而非 0%。
- [prompt 变长] 携带句子清单会增加 token → 截断到固定预算，且只在"多平台同发"时启用。
- [平台窗口与用户期望冲突] 用户可能想要更长的公众号 → 窗口是**默认值**，必须能从配置到达
  （遵循本仓库"默认值 ≠ 写死值"的规矩）。

## Migration Plan

- 无数据迁移；新检查在既有质检里新增条目，旧的成稿仍可复算。
- 回滚：去掉检查与 prompt 片段即可，不留兼容分支。

## Open Questions

- **10% 这个阈值是否合理？** 可以在真实素材上校准后再定（现在先用它做验收基线，
  标注 `needs-validation`）。
- 公众号"小标题"的识别口径（`##` / 加粗 / 独立短行）需要与前端渲染保持一致 ——
  实现时以**渲染出来的样子**为准，而不是以 markdown 源码为准。
