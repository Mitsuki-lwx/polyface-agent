# Design

## Context

动机与证据见 `proposal.md`。设计只依赖这些已确认的事实：

- **没有** `faulthandler` / 信号处理器 / `atexit` → 原生崩溃零证据。
- `scripts/start.sh` 末尾是裸 `wait`（等**全部**子进程）→ 半死状态无人发现。
- `scripts/start.bat` 用 `start ... cmd /k` 起**独立窗口** → 脚本本身不管子进程生死。
  ⚠️ 本环境**无法执行 `.bat`**（`cmd.exe` 被拦），批处理只能做到"逻辑对齐 + 声明未实机验证"。
- 日志目录：`scripts/start.sh` 里是 `$ROOT/logs`；`doctor.py` 有自己的探测。
- `Check(..., info_only=True)` 这套"非阻塞提示"已经存在（Langfuse 那条在用）。

## Goals / Non-Goals

**Goals**

- 下一次崩溃时，日志里**有栈**、有 pid、有退出码。
- 只要有一个服务死了，**启动脚本当场报出来**并收掉另一个。
- 用户能用一条命令确认"服务还活着吗"。

**Non-Goals**

- **不修那个 `0xC0000409` 本身** —— 它没有稳定复现路径，本轮的目标是"下次能定位"（见 Open Questions）。
- **不自动重启**：静默重启会把问题藏起来，而且会让"生成跑到一半服务换了"变成新的坑。
- 不做崩溃上报 / 不联网。
- 不改 `stop.sh` 的既有语义。

## Decisions

### D1：用 `faulthandler`，不用第三方崩溃采集

- 标准库、零依赖、能覆盖 `SIGSEGV/SIGABRT/SIGFPE` 这类**原生层**崩溃（`atexit` 覆盖不到）。
- **必须显式给 `file=`**：默认写 `stderr`，而 `start.sh` 把 stderr 重定向进日志文件 ✓ ——
  但 `cmd /k`（`.bat`）那侧的 stderr 是**窗口**不是文件 ✗，所以统一写**文件**最稳。
- 被否：`sys.excepthook` —— 只接 Python 异常，接不到原生崩溃。

### D2：退出记录由**监管者**记，不由进程自己记

崩溃时进程没有机会跑收尾代码 ✗。所以"退出码 + 谁退的"只能在 `start.sh` 里记 ✓
（它 `wait` 得到退出码 ✓）。进程内只记**启动**与**正常退出**（`atexit`）。

### D3：`start.sh` 用 `wait -n` 逐个等待；`.bat` 靠**独立窗口**

```bash
wait -n "${PIDS[@]}"       # 任一退出即返回
```
然后定位是哪个、报出来、`cleanup`。**不重启**。
被否：轮询 `kill -0` —— 有延迟且拿不到退出码；`wait -n` 直接给码。

⚠️ **`set -euo pipefail` 陷阱（实测踩到两次）**：`wait -n` 与 `wait <pid>` 在子进程异常退出时
都返回非零 → 脚本会**直接跳出**，连"是哪个退了"都来不及打 ✗。两处都必须显式接住状态码。

**`.bat` 是另一种模型**：它用 `start ... cmd /k` 起两个独立窗口后**就退出**，
父进程不持有子进程。强行改成轮询监管会把"启动即用"的体验变成"必须留着一个控制台" ✗，
而 `.bat` 也没有 `wait -n` 的等价物。实际行为已经满足"被看见"：服务死掉时，
**它自己的窗口当场打印 traceback 并停住** ✓ —— 代价只是脚本要把日志路径说清楚。
因此本 change 对 `.bat` 只做后者，并**如实声明未实机验证**。

### D4：`doctor` 的存活检查要**真的打请求**

看进程名会误判（同名进程 / 端口被别的程序占），看端口也没用（监听但不响应）。
打 `GET http://127.0.0.1:<port>/health`（Python）与 `GET /api/materials?limit=1`（Java，
带 `Host: 127.0.0.1:<port>` 以免被 ADR-027 的闸门挡掉 ✗ —— 这条**必须**注意，
否则自查会误报"服务不可达"）。超时 2 秒，`info_only=True`（非阻塞）。

### D5：崩溃日志放进既有 `logs/` 目录

`logs/crash-python.log`。不新增配置项也够用；但按项目"任何可调值都要能到达"的规矩，
给一个 `POLYFACE_CRASH_LOG` 覆盖（默认就是上面那个路径）。

## Risks / Trade-offs

- [`faulthandler` 在 Windows 上对 `0xC0000409` 能否真的抓到栈] → **不确定**（它是
  "fail-fast"，可能直接终止）。所以本 change **不把宝押在它上面**：退出码 + 谁退的
  这两条由脚本保证 ✓，栈是"能拿到更好"。若实测抓不到，如实记录并降级为"至少知道它死了"。
- [`wait -n` 在 Git Bash 的 bash 版本] → 4.3+ 才有；本机是 5.x ✓，但脚本要**探测**一次
  并在不支持时退回"轮询 + 退出码尽力而为"，不能因为一个 bash 特性直接坏掉 ✓。
- [`doctor` 打请求给运行中的服务带来副作用] → 只打 `GET` 且不带副作用（`/health`、
  `materials?limit=1`）✓。
- [`start.bat` 无法实机验证] → 逻辑对齐 + 交付时**明说**未验证。

## Migration Plan

- 无数据迁移。回滚 = 回退这几个文件。
- 验证：故意 `kill -9` 掉 Python 服务 → `start.sh` 必须当场报出退出码 ✓；
  `doctor` 必须报"不可达" ✓。

## Open Questions

- **那个 `0xC0000409` 的根因是什么？**
  可以安全地晚点回答：本 change 只保证"下次发生时能定位"，不改变任何行为约定。
  已知线索：崩溃时最后一条请求是 `GET /favicon.ico 404`；进程已运行 24 分钟；
  同进程内当时启用着 Langfuse（后台导出线程）与 httpx 客户端。
  **标记为 needs-validation**，不猜。
