# Design

## Context

- `ffmpeg` 已在 PATH（既有依赖 ✓，粗剪/封面都在用）
- 视觉能力**实测可用**：`deepseek-v4.1-flash-1017` 能准确描述图像 ✓
- 既有 `llm.py` 是文本客户端；多模态要额外的请求形态（`content: [{type:image_url}]`）
- 既有 `/probe` 已能拿时长/分辨率（ffprobe ✓）

## Decisions

### D1：两段式抽帧 —— 先场景变化，不够再等距补足

`ffmpeg -vf "select='gt(scene,0.3)',scale=640:-1"` 取场景切换帧 ✓；
若不足 N 张，用等距抽样补足 ✓（保证短视频/静态画面也有帧 ✓）。
**不上来就等距** ✗ —— 一个 10 分钟的固定机位直播，等距会得到 10 张一样的图 ✓。

### D2：帧压到 640 宽、JPEG 质量 3

送模型不需要原分辨率 ✓；640 宽足够认内容 ✓，token 与传输都可控 ✓。
帧**另存一份**到 `assets` 供后续复用 ✓（不只活在请求里）。

### D3：描述模板固定三问

"画面里是什么 / 适合放在视频什么位置 / 有没有文字"。三个问题覆盖**可用性**判断 ✓，
而不只是"美不美" ✗（后者不可判定 ✓）。

### D4：视觉调用独立于 `llm.chat_json`

`llm.py` 面向纯文本 JSON ✓。视觉要走 `content` 数组 ✓ —— 新写一个 `vision.describe(image_path, prompt)`，
**复用同一份 base_url / key / 超时** ✓，不新造配置 ✗。

### D5：失败降级只降描述，不降帧

模型挂了 → 帧仍然落盘 ✓ + 描述为空 + 明确报错 ✓。**不编造描述** ✗。

## Risks / Trade-offs

- [场景检测阈值] 0.3 是经验值；静态画面可能抽不满 → 等距补足兜底 ✓
- [成本] 5~10 帧 × 每条视频 —— 勾选式调用，不做默认 ✓
- [隐私] 帧会发给模型 ✗ —— 与素材正文一致（ADR-017 已声明），但要在 UI 上说清楚 ✓

## Non-Goals

- **不做**"按画面自动重排剪辑" ✗（本期先证明能看懂）
- **不做**视频内容检索（跨视频找镜头）✗
