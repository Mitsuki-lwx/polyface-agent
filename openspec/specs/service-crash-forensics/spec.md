# service-crash-forensics Specification

## Purpose
本地服务的**崩溃取证与可见性**：服务意外退出时，必须留下足以定位的证据，
并且必须在**用户还没困惑之前**被明确告知。存在的理由是一个具体事故 ——
Python 服务以 `STATUS_STACK_BUFFER_OVERRUN` 静默退出，日志里连一行 traceback 都没有。

## Requirements

### Requirement: 致命错误留下栈

服务进程收到致命信号或原生层崩溃时 MUST 把**当时的 Python 调用栈**写进**文件**
（而不是只写 stderr）—— 用户是在日志里找问题，不是在终端的历史滚动里找。

#### Scenario: 服务收到致命信号

- **WHEN** 服务进程收到 `SIGSEGV` / `SIGABRT` / `SIGFPE` 等致命信号（或 Windows 上的等价失败）
- **THEN** 崩溃日志文件里出现一份可读的 Python 栈，含线程名与当前帧

#### Scenario: 正常退出不产生噪音

- **WHEN** 服务被正常停止（`Ctrl-C` / `stop.sh`）
- **THEN** 崩溃日志里**不出现**崩溃栈（正常退出≠崩溃）

### Requirement: 生命周期可追溯

服务 MUST 在启动与退出时各留一条记录，含：`pid`、启动时间、**退出码**、
以及（能拿到的话）退出原因。这样"它是什么时候没的"无需考古。

#### Scenario: 事后确认"什么时候死的"

- **WHEN** 服务已退出
- **THEN** 日志里能找到它的启动记录与退出记录，二者之间是它的存活区间

### Requirement: 子进程退出必须被看见

启动脚本 MUST 让"哪个服务停了"在**用户面前**可见，并 MUST 给出日志文件路径：

- **`start.sh`（前台监管）**：对**每个**子进程**分别**等待；任一退出时明确指出
  是**哪一个**、② 它的**退出码**、③ 日志文件路径，并停止其余子进程。
- **`start.bat`（两个独立窗口）**：每个服务在自己的 `cmd /k` 窗口里运行 ——
  窗口里出现 traceback 并停住，即为该服务已停止；脚本 MUST 在就绪时把
  三份日志的路径打印清楚，让用户不必猜。

**MUST NOT** 在"一个服务已死、另一个还活着"的状态下继续显示"运行中"。

#### Scenario: 只死了一个

- **WHEN** Python 服务中途退出而 Java 仍在运行
- **THEN** 启动脚本立即打印"Python 服务已退出（退出码 N），日志：…"，并停止 Java 后退出

#### Scenario: 两个都正常

- **WHEN** 两个服务都在运行
- **THEN** 行为与现在一致（按 `Ctrl-C` 才停止）

### Requirement: 用户能自查"服务还活着吗"

`doctor` MUST 提供一个**真的打一次请求**的存活检查（不是看进程名、不是看端口是否被占），
并 MUST 在两个服务任一不可达时给出**非阻塞的明确提示**（含日志路径）。

#### Scenario: 服务已死但端口还占着

- **WHEN** 端口有监听但请求无人应答，或进程已退出
- **THEN** 自查输出明确说"服务不可达"，并指向对应日志

### Requirement: 不自动重启

服务退出后 MUST NOT 被脚本静默重启。崩溃要**被看见**，不能被掩盖。

#### Scenario: 崩溃后

- **WHEN** 服务崩溃
- **THEN** 脚本报告后退出；用户重启是**显式动作**
