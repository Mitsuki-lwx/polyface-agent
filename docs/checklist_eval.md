# checklist —— 生成管线评测集（防退化）

上游：`docs/spec_eval.md`　　tasks：`docs/tasks_eval.md`

> 每一项都必须**可勾选、可观测**。不许出现「实现完整」「质量良好」这类无法判定的项。
> **至少一条端到端验收**（§8）。验收完必须如实填 §9 与「未做」。

## 1. 默认值表（**每一项都必须能被覆盖**）

| 项 | 默认值 | 覆盖方式 | 说明 |
|---|---|---|---|
| 素材条数 | 10 | `--limit N` | 素材集实际条数；少于 N 时以实际为准 |
| 平台集合 | `xhs,douyin,gzh,zhihu,bilibili` | `--platforms a,b,c` | 5 个全跑 |
| 输出目录 | `eval/reports/<时间戳>/` | `--out DIR` | 每次跑分一个新目录 |
| 复用已有结果 | 开 | `--no-reuse` | 关掉则全部重跑 |
| 单条素材超时 | **自动**（`max(600, 400×平台数)`；5 平台 = 2000s） | `--timeout SEC`（`-1`=不限） | 写死 600s 会把 5 平台的正常长跑误判成超时 —— 整条素材的格子全废、污染基线（实测踩到） |
| 并发 | 1 | `--jobs N` | **默认串行**：并发会被 429（见 MEMORY） |
| 素材集版本 | `MANIFEST.json` 里的值 | 改 manifest | 改动等同于改测试基准 |
| 断言阈值（标题上限/正文上下限/标签上限） | **自动取自 `platform-dna/*.yaml`**，每平台一套 | `--rules FILE` 做**全局覆盖**（调试用） | 断言函数里**不许写死**；取值优先级见 `scripts/eval/dna_rules.py` |

**验收**：上表每一行都要在 §2 里有对应的「改了它，行为确实变了」的观测。

## 2. 参数可改（**本轮的核心验收**）

- [ ] `--limit 3` → 报告里实际参与矩阵的素材是 **3 条**（不是 10 条）
- [ ] `--platforms xhs` → 报告里只有 1 个平台，格子数 = 素材数 × 1
- [ ] `--out /tmp/x` → 报告真的落在 `/tmp/x`，不在默认目录
- [ ] `--no-reuse` → 已有结果的格子**重新跑了**（日志里能看到它又调了一次）
- [ ] `--timeout 1` → 立刻出现「调用失败（超时）」归因，且**不中断整轮**
- [ ] `--jobs 2` → 素材级并行（`ThreadPoolExecutor`）；默认 1=串行（上游限流，见 MEMORY）
- [ ] `--dry-run` → **不发任何 LLM 请求**，只打印预计格数与调用次数

> 判据：任一行改了而行为没变 → 该项**不通过**，回到 T9。

**已知局限（实现时发现，如实记）**：`--timeout` 用看门狗线程实现，
而 Python 杀不掉正在跑的线程 —— 被判定超时的那次调用**可能仍在后台跑完**。
对跑分结论无影响（该格已记为失败），但会让上游多花一次额度。

## 3. 素材集

- [ ] `eval/corpus/` 下有 10 条素材文件，`MANIFEST.json` 与之一一对应
- [ ] manifest 记录了：素材集版本、条数、每条的数字/专有名词计数、生成时的 prompt 指纹、模型名
- [ ] 每条素材长度落在 300~2000 字（`docs/50` §2.1 的口径）
- [ ] 每条素材**至少含 2 个数字**（否则 A1 断言没有咬合点）
- [ ] 删掉一条素材文件 → 跑分器**明确报错**，而不是静默少跑一条
- [ ] 素材文件头部注明「改动等同于改测试基准」

## 4. 断言

- [ ] A1 正文数字无依据 → 红
- [ ] A2 出现素材外的年份 → 红
- [ ] A3 标题为空 / 重复 / 超长 → 红
- [ ] A4 正文长度越界 → 红
- [ ] A5 标签含 `#` / 数量不足 → 红；**超过平台上限 → 红**（上限来自 DNA 的 `tags.count_max`）
- [ ] A6 `video_native` 平台缺 `clip_sheet` → 红；分镜序号不连续 → 红
- [ ] A7 QA 未通过 → 红
- [ ] A8 出现站外导流（手机号 / 邮箱 / 站外链接 / 微信号）→ 红；「评论区聊聊」这类正常互动引导**不误报**
- [ ] **全合规产物 → 全绿**（不误报）
- [ ] 断言层**不调 LLM**：把 `llm.chat` / `llm.chat_json` 换成会抛异常的桩，
      跑完全部断言仍全绿（`test_assertions_never_call_llm`）—— 用**行为**证明，不用 grep 源码
- [ ] 阈值改动（如把标题上限调小）→ 原本通过的产物变红

## 4b. platform-dna 接入（**平台 DNA 实验台**）

评测集原先只用默认阈值，`platform-dna` 里的 `body_chars_max` / `tags.count_max` /
`title_chars_max` **一条都没用上** —— 于是「改了某平台的 DNA，产出有没有变好」根本答不了。
（实测例子：`m02/bilibili` 的「正文超长 1024字 > 上限1000字」是产品自己的 QA 抓到的，
A4 用的默认 `body_max=20000` 根本不会报。）

- [ ] `--dry-run` 打印的 `rules_by_platform` 里，5 个平台的阈值都来自 DNA：
      xhs `title_max=20 body_max=1000 tags_max=6`、douyin `55/2200/5`、
      gzh `64/20000/3`、zhihu `100/无上限/5`、bilibili `80/2000/10`
- [ ] **知乎的 `body_chars_max: 0` 必须识别成「无上限」**，不能掉进 `normalize_limits` 的默认值 1000
      （早先的分支顺序踩过这个坑 —— 凭空给知乎加了个上限，且看起来一切正常）
- [ ] B站用 `specs.desc_chars_max`、抖音用 `specs.caption_chars_max`（各平台字段名不统一）
- [ ] 报告里含 **DNA 指纹**（每平台一个 + 合并一个）
- [ ] 报告里含**分平台切片**表（改了 xhs 的 DNA，就要能只看 xhs 那几格）
- [ ] 基线对比时，**DNA 指纹不同 → 标为「不可比」**，不静默比较
- [ ] `sources` / `updated_at` 变了**不影响**指纹（否则补个来源链接就把报告全标成不可比）
- [ ] `python scripts/doctor.py` 会报平台 DNA 的新鲜度；超期给**提示**（非阻塞）
- [ ] `POLYFACE_DNA_MAX_AGE_DAYS` 可配；乱填/非正数退回默认

## 5. 跑分器

- [ ] 跑到一半中断 → 已完成的格子结果**仍在盘上**
- [ ] 再跑 → 只跑剩下的格子（日志里能看到跳过的）
- [ ] 429 / 超时 → 该格记入「调用失败」，**不**记入「断言失败」
- [ ] 单格失败**不中断整轮**
- [ ] 报告里 prompt 指纹 / 模型名 / 耗时 / token 用量**齐全**
- [ ] 同一份产物重跑断言 → 结论完全一致（判定确定性）

## 6. 变异测试（**必须做，绿不等于有效**）

- [ ] 把 A1（数字有依据）的实现注释掉 → 对应测试**变红** → 还原
- [ ] 把 A6（`clip_sheet`）的实现注释掉 → 对应测试**变红** → 还原

## 9. 诚实边界（验收时必须如实填）

- [ ] 明确记录：**合成素材不能论证"产品有没有用"** —— 它只测"同一批输入下产出有没有变差"
- [ ] 明确记录：单模型基线，**未**做多模型横向对比
- [ ] 明确记录：本版**未**接 CI
- [ ] 明确记录：断言是**性质断言**，不是"像不像人写的"的质量分
- [ ] 明确记录：LLM 非确定性 → 通过率会有波动，**不能**把单次 ±1 格的波动当退化
- [ ] 明确记录：**A1 有两类已知误报，不打算修**（加阈值就是"为了让测试变绿而调参"）：
      1. **成语化数字** —— 「比说**一百句**都管用」「从**0到1**的第一步」不是事实主张；
      2. **派生算术** —— 素材说「月入3000、日投入1.5小时」，稿件算成「一个月45小时、时薪66块」——
         是可推导的新断言，判不判看立场。
      两者都会让该格判 FAIL。**看报告时要认得出来**，别当成真退化。

## 实测（2026-10-07）

**素材生成**：10 条一次跑通，436~1334 字（平均 847），每条都满足特征下限。
实际服务模型 `glm-5.2` 5 次 / `deepseek-v4-flash` 7 次 / `deepseek-v4-pro` 1 次 ——
**配置里写的 `deepseek-v4-flash` 只服务了 7 次**，其余是额度耗尽后的自动降级。
（只记配置值就是在写一个没发生过的实测值，所以 manifest 里记的是实际分布。）

**单元测试**：Python 427 passed / 3 skipped。

**冒烟真跑**（1 条素材 × 2 平台，两轮）：

| 轮次 | 结果 | 说明 |
|---|---|---|
| 第 1 轮 | 0/2 | A1 误报 `['99']`（素材用中文数字）+ xhs `LLMParseError` |
| 第 2 轮（修 A1 后） | 1/2 | A1 误报消失；douyin `LLMParseError` |

**全量跑分**（5 平台 × 10 条）：尝试两次，**均被上游中断**，未拿到完整基线。

| 次 | 结果 |
|---|---|
| 第 1 次 | 1 小时上限截断；m04~m10 因上游额度/网络问题全灭 |
| 第 2 次 | m01~m02 跑完（10 格，6 通过）；m03 起 `LLMNetworkError` —— 端点 `token.sensenova.cn` **完全不可达**（curl 000 / SSL EOF），而 github/pypi/huggingface 正常 |

**离线复算**（用存下来的真实草稿重跑断言，不花额度）：修掉三处数字 bug 后，
m01~m02 十格从 6/10 提到 **8/10**。剩下两格是 §9 记的两类**已知误报**。

**单条素材耗时**：约 270~970 秒（5 平台，含限流重试）。

**顺带发现的第二个产品问题（已修，2026-10-07）**：`llm.chat_json` 对 JSON 解析失败
**没有重试** —— 模型一次返回坏 JSON 就整个平台失败。冒烟两轮 4 次草稿调用里中招 2 次
（`LLMParseError: Expecting ',' delimiter`）。

修法：新增可配项 `LLM_JSON_RETRIES`（`.env`，默认 `2`），`chat_json` 解析失败时
带退避重试；每次失败都进用量日志（否则"多常发生"只能靠翻日志猜）。
**取 2 而不是沿用 `LLM_MAX_ATTEMPTS=3`**：避免与模型降级链的重试相乘。

验证：10 条单测（失败后成功 / 一直失败则抛且次数恰好 / 首次即成功只调一次 /
可配项真的起作用 / 记用量）；变异测试两条都变红后还原；
真链路正常路径复验通过（`glm-5.2`，7.8s）。
**重试本身在真实坏 JSON 上的触发未复现**（坏 JSON 是偶发，无法按需制造）。

## 顺带修的一处**既有产品问题**（不是本评测集引入的）

做 A1 断言时发现 `app/pipeline/generate.py::_rule_qa` 的「数字依据」校验
**只比对阿拉伯数字**，中文数字一律看不见。实测复现：

```
素材事实：付费专栏定价九十九，卖了四百多份
稿件正文：我搭了付费专栏，定价99，卖了400多份。
→ 修前告警：正文含素材中无依据的数字: 400、99（请确认或删除）
```

它让用户去删一个**明明有依据**的数字。评测集首次跑分时 A1 报了同样的 `['99']`，
顺着查才定位到产品里也有 —— 两边必须同一套口径，否则评测集测的不是线上那条路。

**修法**（`app/pipeline/zhnum.py` 新增 + `_rule_qa` 改用它）：

| 侧 | 策略 | 为什么 |
|---|---|---|
| 素材（事实清单） | **宽松**：中文数字都算依据 | 否则素材写「三」、稿件写「3」会误报 |
| 稿件（正文） | **严格**：只查像数字的中文数字（带单位或 ≥2 位） | 否则「迈出**这一步**」里的「一」会被当成数字去比对 |

修后实测：等价数字**不再告警**；真幻觉 `199` **照样抓**；成语「这一步」**不误报**。
回归测试 4 条加在 `python-service/tests/test_num_basis.py`。
