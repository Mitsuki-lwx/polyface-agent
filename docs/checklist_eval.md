## 1. 默认值表（**每一项都必须能被覆盖**）

| 项 | 默认值 | 覆盖方式 | 说明 |
|---|---|---|---|
| 素材条数 | 10 | `--limit N` | 素材集实际条数；少于 N 时以实际为准 |
| 平台集合 | `xhs,douyin,gzh,zhihu,bilibili` | `--platforms a,b,c` | 5 个全跑 |
| 输出目录 | `eval/reports/<时间戳>/` | `--out DIR` | 每次跑分一个新目录 |
| 复用已有结果 | 开 | `--no-reuse` | 关掉则全部重跑 |
| 单条素材超时 | **自动**（`max(600, 400×平台数)`；5 平台 = 2000s） | `--timeout SEC`（`-1`=不限） | 写死 600s 会把 5 平台的正常长跑误判成超时 —— 整条素材的格子全废、污染基线（实测踩到） |
| 并发 | 1 | `--jobs N` | **默认串行**：并发会被 429（见 MEMORY） |
| 素材集版本 | `MANIFEST.json` 里的值 | 改 manifest | 改动等同于改测试基准 |
| 断言阈值（标题上限/正文上下限/标签上限） | **自动取自 `platform-dna/*.yaml`**，每平台一套 | `--rules FILE` 做**全局覆盖**（调试用） | 断言函数里**不许写死**；取值优先级见 `scripts/eval/dna_rules.py` |

**验收**：上表每一行都要在 §2 里有对应的「改了它，行为确实变了」的观测。

## 2. 参数可改（**本轮的核心验收**）

- [ ] `--limit 3` → 报告里实际参与矩阵的素材是 **3 条**（不是 10 条）
- [ ] `--platforms xhs` → 报告里只有 1 个平台，格子数 = 素材数 × 1
- [ ] `--out /tmp/x` → 报告真的落在 `/tmp/x`，不在默认目录
- [ ] `--no-reuse` → 已有结果的格子**重新跑了**（日志里能看到它又调了一次）
- [ ] `--timeout 1` → 立刻出现「调用失败（超时）」归因，且**不中断整轮**
- [ ] `--jobs 2` → 素材级并行（`ThreadPoolExecutor`）；默认 1=串行（上游限流，见 MEMORY）
- [ ] `--dry-run` → **不发任何 LLM 请求**，只打印预计格数与调用次数

> 判据：任一行改了而行为没变 → 该项**不通过**，回到 T9。

**已知局限（实现时发现，如实记）**：`--timeout` 用看门狗线程实现，
而 Python 杀不掉正在跑的线程 —— 被判定超时的那次调用**可能仍在后台跑完**。
对跑分结论无影响（该格已记为失败），但会让上游多花一次额度。

**规模**：5 平台 × 10 条素材 = **50 格**，全部跑完（0 缺失）。
**模型**：`cline-pass/deepseek-v4.1-flash`（真实，非 mock）　**prompt 指纹** `50bb64dff13578a1`
**DNA 指纹** `b7a9fe6326d38a7c`

| 指标 | 值 |
|---|---|
| 格子总数 | 50 |
| **通过** | **26** |
| 断言失败 | 21 |
| 调用失败（超时/网络，**非**质量信号） | 3 |
| **通过率** | **52.0%** |

**分平台**（这个差异本身就是结论）：

| 平台 | 通过 | 断言失败 | 说明 |
|---|---|---|---|
| gzh | 8/10 | 1 | 最好。公众号正文上限 20000 字、标题 64，模型够用 |
| zhihu | 6/10 | 3 | |
| xhs | 5/10 | 5 | **4 次全是标题超 20 字上限** |
| douyin | 4/10 | 5 | |
| bilibili | 3/10 | 7 | 最差，且 6 次是 QA 拦下的幻觉 |

**失败归因**：

| 断言 | 次数 | 判读 |
|---|---|---|
| **A7 通过质量门** | **15** | **产品自己的 QA 抓到的问题 —— 主要是模型幻觉**，不是评测集的噪声 |
| A1 数字有依据 | 5 | 混合：2 处已知误报 + 3 处判断类（见下） |
| **A3 标题合法** | **4** | **全部在 xhs**，标题 22~30 字突破 20 字上限 —— 接 DNA 之前**完全测不出来**（默认上限是 40） |

A7 的 15 次里，理由都很具体，例如：

```
m01/bilibili  「收入不稳定带来的焦虑是真实的」素材中无对应事实，属于新增主观断言
m02/zhihu     「买课前我会检查」及 4 条检查清单，素材未提及
m03/douyin    「连交下个月伙食费286块这种小事都能漏」素材只说"要交286块"，没说被漏交
m03/gzh       「两个人都没记住」素材只说"我忘了接老大放学"，未说妻子也没记住
m03/bilibili  「半年真实数据」素材里没有任何时间跨度信息
```

**这说明事实约束那道闸门在正常工作**，同时也说明 `deepseek-v4.1-flash`
在"合理推断"与"编造"之间越界频繁（把"要交286块"写成"漏交了286块"、凭空加"半年数据"）。

**耗时**：单条素材 600~1900s（5 平台 × 各 3~4 次调用）；整轮约 **5 小时**，
被 1 小时执行上限切成 **5 段**续跑（`--out` 指回同一目录即自动跳过已完成）。

### 跑这一轮时抓到的产品 bug（都已修 + 回归测试）

评测集第一次跑就抓出 **5 类**数字口径问题，产品 `_rule_qa` 与评测断言共用同一套，两边同时修：

| # | 现象 | 后果 |
|---|---|---|
| 1 | `成` 在数字中间 → `UNITS["成"]` KeyError | **生产崩溃**：任何含「成」的稿件让整个平台生成失败 |
| 2 | 阿拉伯数字 + 成（`3成`）不被识别 | 稿件「闲鱼3成」与素材「三成」对不上 |
| 3 | 数字与单位间有空格（`1200 万`） | 只提取到 `1200` |
| 4 | 视频时间码（`【15-40s 干货】`） | douyin 稿件的 15/40/55 全被当成事实数字 |
| 5 | 年月简写（`2022.5`） | 与素材的「2022年5月」对不上 |
| 6 | **`70kg` 被当成 `70k`=70000** | 体重类数字全部算错（`k` 单位撞上 `kg`） |
| 7 | 无标点数字列表（`1 先攒… 2 先接…`） | 裸 `2` 被当成事实数字 |

**另加两条断言**（都由 DNA 驱动）：**A8 站外导流**（手机号/邮箱/外链/微信号）、
**A5 标签上限**（平台罚的是堆砌，不是太少）。

### 关于 `LLM_TIMEOUT_SEC`：60 秒在制造失败

实测（同一模型，139 次调用）：

| | 中位 | 最大 |
|---|---|---|
| 成功 | 33.8s | **105.2s** |
| 失败 | **60.6s** | 65.4s ← 全部卡在 60 秒上限 |

改成 150 秒后，失败率从 **20~38% 降到 7~9%**。
只写进 `.env.example` 与两份 README 的提示，**没动默认值** —— 凭一家服务商改默认是过拟合。

### 已知误报（**不修**，如实记录）

A1 剩下的 5 次里，2 次是这两类：

1. **成语化数字** ——「从**0到1**的第一步」不是事实主张
2. **比率写法** —— 稿件写「5:3:2」，素材写「三成/五成/两成」。机械判定分不清"比率"与"三个数"

另有 3 次属**判断类**，倾向认为是真问题但可争议：

3. **四舍五入** —— 素材「249.03亿」、稿件写「249亿」
4. **时间简写** —— 素材「半马2小时05」、稿件写「半马205」
5. **量词粘连** —— 素材「四百七十五」、稿件「四百七十五一克」被读成一个数

> 加规则去躲它们就是猜。**看报告时要认得出来**，别当成真退化。

## 指标问题：二值通过率噪声太大（2026-10-09 实测）

**同一份代码、同一批素材、连跑 3 次**（m01~m05 × xhs）：

| | 二值通过率 | 原子支持率 |
|---|---|---|
| 第 1 次 | 80.0%（4/5） | 99.03%（原子 102/103） |
| 第 2 次 | 60.0%（3/5） | 100.00%（98/98） |
| 第 3 次 | 80.0%（4/5） | 98.96%（95/96） |
| **波动幅度** | **20.0%** | **1.04%** |

5 格里 3 格（m01/m02/m05）在**同样条件下会翻面**。也就是说：

- **±10 点以内的通过率差异都在噪声带里** —— 之前几轮"52%→60%→78%→62%"的对比，
  除了**机制性修复**（如标题上限）以外，**统计上都不能下结论**
- 这正是 `Quantifying Variance in Evaluation Benchmarks`（arXiv 2406.10229）说的问题：
  评测被用来做决策，却几乎没人量化方差

### 改法：原子事实支持率（FActScore 口径，arXiv 2305.14251）

该论文原话：*"generations often contain a mixture of supported and unsupported pieces...
making **binary judgments of quality inadequate**"* —— 正是我们的病。

所以让断言**带上原子计数**（`Result.checked` / `Result.failed`）：
A1 逐个数字、A2 逐个年份、A9 逐个专名本来就在查原子级的东西，只是结果被压成了二值。
现在报告同时出两个指标：

- **原子支持率**（稳，1.04% 波动）—— 回答"错了多少"
- **二值通过率**（噪声大）—— 回答"能不能直接发"

**两者都要，不能只留一个**：支持率 99% 也可能有 40% 的格子不可发布 ——
说明**失败是少数但每一个都致命**（一条编造的断言就废掉整篇），而不是"整篇在编"。

**已知不精确**：同一个年份会同时被 A1（数字）与 A2（年份）各计一次，
所以支持率有轻微重复计数。不影响"稳不稳"的结论，但别把它当精确比例读。

## 顺带修的一处**既有产品问题**（不是本评测集引入的）

做 A1 断言时发现 `app/pipeline/generate.py::_rule_qa` 的「数字依据」校验
**只比对阿拉伯数字**，中文数字一律看不见。实测复现：

```
素材事实：付费专栏定价九十九，卖了四百多份
稿件正文：我搭了付费专栏，定价99，卖了400多份。
→ 修前告警：正文含素材中无依据的数字: 400、99（请确认或删除）
```

它让用户去删一个**明明有依据**的数字。评测集首次跑分时 A1 报了同样的 `['99']`，
顺着查才定位到产品里也有 —— 两边必须同一套口径，否则评测集测的不是线上那条路。

**修法**（`app/pipeline/zhnum.py` 新增 + `_rule_qa` 改用它）：

| 侧 | 策略 | 为什么 |
|---|---|---|
| 素材（事实清单） | **宽松**：中文数字都算依据 | 否则素材写「三」、稿件写「3」会误报 |
| 稿件（正文） | **严格**：只查像数字的中文数字（带单位或 ≥2 位） | 否则「迈出**这一步**」里的「一」会被当成数字去比对 |

修后实测：等价数字**不再告警**；真幻觉 `199` **照样抓**；成语「这一步」**不误报**。
回归测试 4 条加在 `python-service/tests/test_num_basis.py`。
