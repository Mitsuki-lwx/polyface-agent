## 1. 默认值表（**每一项都必须能被覆盖**）

| 项 | 默认值 | 覆盖方式 | 说明 |
|---|---|---|---|
| 素材条数 | 10 | `--limit N` | 素材集实际条数；少于 N 时以实际为准 |
| 平台集合 | `xhs,douyin,gzh,zhihu,bilibili` | `--platforms a,b,c` | 5 个全跑 |
| 输出目录 | `eval/reports/<时间戳>/` | `--out DIR` | 每次跑分一个新目录 |
| 复用已有结果 | 开 | `--no-reuse` | 关掉则全部重跑 |
| 单条素材超时 | **自动**（`max(600, 400×平台数)`；5 平台 = 2000s） | `--timeout SEC`（`-1`=不限） | 写死 600s 会把 5 平台的正常长跑误判成超时 —— 整条素材的格子全废、污染基线（实测踩到） |
| 并发 | 1 | `--jobs N` | **默认串行**：并发会被 429（见 MEMORY） |
| 素材集版本 | `MANIFEST.json` 里的值 | 改 manifest | 改动等同于改测试基准 |
| 断言阈值（标题上限/正文上下限/标签上限） | **自动取自 `platform-dna/*.yaml`**，每平台一套 | `--rules FILE` 做**全局覆盖**（调试用） | 断言函数里**不许写死**；取值优先级见 `scripts/eval/dna_rules.py` |

**验收**：上表每一行都要在 §2 里有对应的「改了它，行为确实变了」的观测。

## 2. 参数可改（**本轮的核心验收**）

- [x] `--limit 3` → 报告里实际参与矩阵的素材是 **3 条**
      **实测**：`--dry-run --limit 3` → `素材 3 × 平台 5 = 15 格` ✓
- [x] `--platforms xhs` → 报告里只有 1 个平台，格子数 = 素材数 × 1
      **实测**：`素材 10 × 平台 1 = 10 格` ✓
- [x] `--out` → 报告真的落在指定目录
      **实测**：`--out .workbuddy-ai/evalout/to` → `report.md` / `report.json` 就在那儿 ✓
- [x] `--no-reuse` → 已有结果的格子**重新跑了**
      **实测**：同一个 `--out`：不加 → `[跳过] m01 已有结果`、**0s**；
      加 `--no-reuse` → 真跑 **191.4s** ✓
- [x] `--timeout 1` → 立刻出现「调用失败（超时）」归因，且**不中断整轮**
      **实测**：`[完成] m01 timeout 0/1 通过 1.0s` → `调用失败 1`、`断言失败 0`，
      整轮正常结束（**没有**崩/中断）✓
- [x] `--jobs 2` → 素材级并行
      **实测**：`--limit 2 --platforms xhs --jobs 2` → 两条**同时**在跑
      （m02 102s 先回、m01 184.9s 后回），**墙钟 192s** ≈ 串行（约 287s）的 2/3 ✓
- [x] `--dry-run` → **不发任何 LLM 请求**，只打印预计格数与调用次数
      **实测**：秒回，输出 `{"materials":10,"platforms":5,"cells":50,"approx_llm_calls":210,...}` ✓

> 判据：任一行改了而行为没变 → 该项**不通过**，回到 T9。

**已知局限（实现时发现，如实记）**：`--timeout` 用看门狗线程实现，
而 Python 杀不掉正在跑的线程 —— 被判定超时的那次调用**可能仍在后台跑完**。
对跑分结论无影响（该格已记为失败），但会让上游多花一次额度。

## 指标问题：二值通过率噪声太大（2026-10-09 实测）

**同一份代码、同一批素材、连跑 3 次**（m01~m05 × xhs）：

| | 二值通过率 | 原子支持率 |
|---|---|---|
| 第 1 次 | 80.0%（4/5） | 99.03%（原子 102/103） |
| 第 2 次 | 60.0%（3/5） | 100.00%（98/98） |
| 第 3 次 | 80.0%（4/5） | 98.96%（95/96） |
| **波动幅度** | **20.0%** | **1.04%** |

5 格里 3 格（m01/m02/m05）在**同样条件下会翻面**。也就是说：

- **±10 点以内的通过率差异都在噪声带里** —— 之前几轮"52%→60%→78%→62%"的对比，
  除了**机制性修复**（如标题上限）以外，**统计上都不能下结论**
- 这正是 `Quantifying Variance in Evaluation Benchmarks`（arXiv 2406.10229）说的问题：
  评测被用来做决策，却几乎没人量化方差

### 改法：原子事实支持率（FActScore 口径，arXiv 2305.14251）

该论文原话：*"generations often contain a mixture of supported and unsupported pieces...
making **binary judgments of quality inadequate**"* —— 正是我们的病。

所以让断言**带上原子计数**（`Result.checked` / `Result.failed`）：
A1 逐个数字、A2 逐个年份、A9 逐个专名本来就在查原子级的东西，只是结果被压成了二值。
现在报告同时出两个指标：

- **原子支持率**（稳，1.04% 波动）—— 回答"错了多少"
- **二值通过率**（噪声大）—— 回答"能不能直接发"

**两者都要，不能只留一个**：支持率 99% 也可能有 40% 的格子不可发布 ——
说明**失败是少数但每一个都致命**（一条编造的断言就废掉整篇），而不是"整篇在编"。

**已知不精确**：同一个年份会同时被 A1（数字）与 A2（年份）各计一次，
所以支持率有轻微重复计数。不影响"稳不稳"的结论，但别把它当精确比例读。

### A7 原子化（2026-10-09）

支持率原先**只覆盖机械检查**（数字/年份/专名），而那部分几乎总是干净的 ——
baseline-v2 里 A7 失败 24 次却贡献 **0 个原子**。现在让 QA
**先把成稿拆成原子断言、再逐条核对**，并报出 `claims_checked` / `claims_unsupported`。

冒烟实测（2 格都通过）：

| 素材 | 二值 | `claims_checked` | `claims_unsupported` | 支持率 |
|---|---|---|---|---|
| m01 | 通过 | 22 | 0 | |
| m02 | 通过 | 32 | **2** | |
| 合计 | **100%** | 54 | 2 | **97.9%** |

**这正是 FActScore 的价值：支持率独立于二值判决** —— 两格都"通过"，它仍看得出瑕疵。

> ⚠️ **一个语义细节**：`claims_unsupported > 0` **不蕴含** `passed=False`。
> QA 会把"可接受的改写"也记进 unsupported 的计数里，但判决上仍可能通过。
> 所以两个指标**测的不是同一件事**：
> · 支持率 = "有多少内容没被素材直接支持"（连续的、稳定的）
> · 二值 = "能不能直接发"（离散的、噪声大的）
> **两个都要看**，不能拿一个替代另一个。

## 顺带修的一处**既有产品问题**（不是本评测集引入的）

做 A1 断言时发现 `app/pipeline/generate.py::_rule_qa` 的「数字依据」校验
**只比对阿拉伯数字**，中文数字一律看不见。实测复现：

```
素材事实：付费专栏定价九十九，卖了四百多份
稿件正文：我搭了付费专栏，定价99，卖了400多份。
→ 修前告警：正文含素材中无依据的数字: 400、99（请确认或删除）
```

它让用户去删一个**明明有依据**的数字。评测集首次跑分时 A1 报了同样的 `['99']`，
顺着查才定位到产品里也有 —— 两边必须同一套口径，否则评测集测的不是线上那条路。

**修法**（`app/pipeline/zhnum.py` 新增 + `_rule_qa` 改用它）：

| 侧 | 策略 | 为什么 |
|---|---|---|
| 素材（事实清单） | **宽松**：中文数字都算依据 | 否则素材写「三」、稿件写「3」会误报 |
| 稿件（正文） | **严格**：只查像数字的中文数字（带单位或 ≥2 位） | 否则「迈出**这一步**」里的「一」会被当成数字去比对 |

修后实测：等价数字**不再告警**；真幻觉 `199` **照样抓**；成语「这一步」**不误报**。
回归测试 4 条加在 `python-service/tests/test_num_basis.py`。

### 关于 §6-4 的一个**教训**（如实记）

判据要的是"改坏一个 prompt → 真跑一轮 → 结论确实变了"。
我先试了两次**改 prompt**（让模型"编数字"、"标题写 45 字以上"）——

换成**产品代码级**的变异（往成稿追加一句编造「88888 次播放」）→ **通过率 100% → 0%** ✓、
`A1 数字有依据：素材里找不到依据的数字：['88888']`（checked 14 / failed 1，支持率 97.37%）✓。
