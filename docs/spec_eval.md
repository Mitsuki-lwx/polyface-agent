# spec —— 生成管线评测集（防退化）

版本：2026-10-07　　对应 tasks：`docs/tasks_eval.md`　　验收：`docs/checklist_eval.md`

---

## 1. 背景

`docs/71` §5 把这件事称为「**当前最大的工程缺口**」，依据是：全仓 `docs/` 里
「评测 / golden / 回归集」**零命中**。

项目其实已经有「测试有没有效」的肌肉 —— 变异测试。但它只覆盖**确定性代码**。
而生成管线里真正决定产出好坏的东西是那 **6 个 system prompt**
（`UNDERSTAND / BRIEF / DRAFT / QA / CLIP / LEARN`），它们是**模块常量，没有版本号**。

于是现在有一个窟窿：**改一句提示词，唯一能发现退化的方式是人工看几篇稿子。**

现有 328 项 Python + 90 项 Java 测试全绿，**不能**说明 prompt 没退化 —— 它们跑在
`LLM_MOCK=true` 下，产出是罐头。而「人工看几篇」这件事，改 prompt 当天还能做，
三个月后就不做了。

## 2. 目标用户

**现阶段只有作者本人**（以及将来接手这个仓库的人）。
不是给终端用户的功能：不接 UI、不做安装引导、不做降级打磨。

## 3. 能力清单（一句话一条）

1. 一份**固定素材集**：若干条输入素材，**冻结在仓库里并带版本号** —— 每次跑用的是同一批输入
2. 素材**可重新生成**（用于扩充或换一批），但**跑分只读冻结的那一批**，生成器不是跑分链路的一部分
3. 素材规格**受控**：每条素材明确含多少个数字、多少个专有名词、多少条可核验断言 —— 断言才有东西可咬
4. 一个**跑分器**：素材集 × 平台矩阵跑一遍**真实**生成，产出通过率
5. 一组**机械性质断言**：每条要么过要么不过，**不引入主观判断、不调用 LLM**
5b. 断言阈值**取自 `platform-dna/*.yaml`**（每平台一套：标题上限 / 正文上下限 / 标签上限）——
   于是改一条平台规则就能只跑该平台、看它那几格的通过率变化。这就是「平台 DNA 的实验台」
6. 每条断言**有反例测试**：喂一个故意违规的产物，该断言必须变红
7. 报告记录 **prompt 指纹**（6 个 system prompt 的哈希）与 **DNA 指纹**（5 个平台 DNA 的哈希）——
    prompt 或平台规则变了，报告看得出来；基线对比时两者任一不同即标「不可比」
8. 与**上一次结果对比**，标出退化：哪些（素材 × 平台）从过变不过；
   报告另有**分平台切片**（改了某平台的 DNA 就要能只看那个平台）
9. 报告含**耗时与 token 用量** —— 成本可见
10. 规模**可配**：素材条数、平台集合、输出目录、是否复用已有结果，都能从命令行改
11. 中途失败**不丢已有结果**（真实跑一次可能几小时，429 是常态）
12. 断言**只读不写**：绝不「顺手修一下产物再判过」

## 4. 非功能要求

- **只在本机**：素材与报告都落在本机；不新增外部依赖，不引入 Node
- **可中断续跑**：跑到一半中断，已完成的（素材 × 平台）结果保留，重跑时跳过
- **成本可预算**：跑之前能算出这次大概要多少次 LLM 调用
- **复用真实管线**：调用现有的生成入口，**不复制一份逻辑** —— 否则测的不是线上那条路
- **判定确定性**：同一产物 + 同一素材 → 断言结论必然相同（LLM 的非确定性只影响产物，不影响判定）
- **失败要能归因**：报告必须区分「断言失败」与「调用失败 / 超时 / 429」

## 5. 设计骨架

三层，边界清晰：

```
素材层（冻结，不联网）  →  跑分层（矩阵 + 续跑 + 报告）  →  断言层（纯函数，不调 LLM）
```

**关键决定一：素材用 LLM 合成后**冻结**，不抓网上的真实语料。**

考虑过 HuggingFace 上的真实中文长文（网络实测可下，467KB 一次成功）。放弃的理由三条：

- HF 上能拿到的是**新闻 / 百科 / 翻译语料**，文体与「博主喂进来的素材」错位 ——
  测出来的退化不一定是用户会遇到的退化；
- 这些数据集**多数没有声明 license**，与项目「只处理自有或已获授权素材」的立场
  （README 合规声明）冲突；
- 合成素材反而有个真实语料给不了的好处：**特征可控** —— 可以刻意让每条素材含确定数量的
  数字与专有名词，断言才有明确的咬合点。

**代价必须写清楚**：合成素材**不能**用来论证「产品有没有用」（那是第三关 `docs/50` 的事），
它只能用来论证「**同一批输入下，产出有没有变差**」。这句话要印在报告抬头。

**关键决定二：断言只做机械判定，不请 LLM 当裁判。**

`docs/71` §5 的原话是「**不追求精确匹配**（LLM 输出本就非确定），只断言性质」。
再加一层 LLM 打分会同时引入两个问题：成本翻倍；且**裁判与被评是同一个模型**，
它的偏好会掩盖被评模型的退化。

**关键决定三：prompt 指纹进报告。**

这是「防退化」闭环里最容易漏的一环：报告若不记录 prompt 指纹，那么「这次通过率涨了」
到底是 prompt 改好了、还是模型换了、还是素材动了 —— 分不清。
指纹让报告**自证其对比是否成立**。

**其它骨架决定：**

- 断言层写成**纯函数**：`(素材, 产物) -> 结论列表`；不读网络、不写文件、不调模型 —— 因此能被普通单测覆盖
- 报告同时出 **JSON（机器读，供 diff）** 与 **Markdown（人读）**
- 素材清单单独一个 manifest 文件，**改动它等同于改测试基准**，必须显式提交
- **素材进仓库、报告不进**：`eval/corpus/` 随代码走（它是测试基准），`eval/reports/` 写进 `.gitignore`
- 断言的**阈值**（标题长度区间、标签个数下限……）全部可配，不写死在断言函数里

## 6. Out of Scope（本版不做）

- **LLM 当裁判打分**（见关键决定二）
- **人工抽检界面**
- **自动改 prompt / 自动调参**
- **粗剪、入料、封面**的评测 —— 本版只评生成管线
- **CI 集成**（先把脚本跑顺；跑一次的成本还不适合进 CI）
- **多模型横向评测**（先把单模型基线立住）
- **竞品对比**
- **「产品有没有用」的判断** —— 那是第三关（`docs/50`），本版不碰
