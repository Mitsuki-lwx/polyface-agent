# 停顿复核 · 交付说明

> `openspec/changes/pause-review-cuts`。交付日期：2026-11-09。

## 一、解决什么

规则剪停顿只看**声学**：静音超过阈值就剪。可是"停 2 秒"有两种，声学上完全一样：

| 现场 | 该不该剪 |
|---|---|
| 卡壳、犹豫、想下一句 | 该剪 |
| 故意留白、强调、换段前的呼吸 | **不能剪** |

差别只在语义 —— 规则永远判不了，所以交给模型，但**只让它投票**。

## 二、怎么做的

| 层 | 内容 |
|---|---|
| `app/pipeline/pausereview.py` | `build_candidates` / `review_candidates` / `apply_verdicts` / `format_report` |
| `prompts.py` | `build_pause_review_prompt` + `SCENE_BUILDERS["pause_review"]`（版本号那一层要管住它）|
| `scripts/roughcut.py` | `--pause-review` / `--pause-review-min` / `--pause-review-max`；结果进 checkpoint |
| Java `RoughcutRunner` | 三个参数透传，**默认不传 = 关** |
| `index.html` | 勾选框 + 数据边界提示 |

### 三条纪律

1. **程序给时间，模型只投票** —— 模型回 `{id, action, why}`；它给的时间戳一律忽略
2. **默认关** —— 开了会把转写文本发给你配的 LLM（ADR-017）
3. **降级要出声** —— 模型挂了 → `llm_skipped=true`，报告写"未执行"，行为退回纯规则

## 四、知道的局限（不藏着）

1. **模型给的理由可能是编的** —— 它没听过音频。所以这里的标准是"可审查"，不是"可解释"：
   理由 + 原句 + 谁做的决定，得摆在界面上给人看。目前界面只显示剪点，**理由还没进 UI**。
2. **模型可能过于保守** —— 实测两例都判 `keep`。prompt 里写了"拿不准就 keep（宁可多留半秒）"，
   这是刻意的；但意味着这个功能更擅长**救回误剪**，而不是**多剪**。效果数据还没有。
3. **候选上限 80** —— 一小时长视频会有更多停顿；超出时只取最长的 80 条（其余不判）。
4. **粒度** —— 只能在停顿边界上做决定；模型想剪"词中间"办不到（也不该办到）。
5. **未验证**：勾选后从界面**点发起**的完整点击流（我用的是直接 POST 同一参数）；
   `.bat` 路径本环境依旧无法执行。

## 五、成本

| 项 | 数值 |
|---|---|
| 调用次数 | **1 次 / 条视频**（不是每个点一次）|
| 输入 | 每条候选 ≈ 60 字上下文；80 条 ≈ 4k token |
| 输出 | ≤ 1k token |
| 钱 | DeepSeek ≈ ¥0.002–0.005；cline-pass 免费通道 = 0 |
| 时间 | ≈ 10s（实测），对比 ASR 40s / 渲染几十秒可忽略 |

## 六、追加：声学特征（openspec/changes/pause-prosody）

模型听不到音频（实测网关对 `input_audio` 返回 **400 Invalid input**），
所以把"怎么说的"算成数字：`rms_slope`（停顿前能量走势）、`pitch_delta`（停顿前后音高差）。

- 只算候选窗口：实测 **45 ms/候选**（40 条 1.81s）
- 音频不出本机，只发数字；没有数据就不发 `prosody` 键
- 开关：`pause_review_prosody`（默认 true）/ `--no-pause-prosody`
- **真模型 A/B**（同一段文字，只换 prosody）：渐弱+音高上扬 → `keep`；
  平稳/渐强 → `cut`。判定被翻转，理由里引用了数字。

踩到的坑：斜率若用"窗口首帧 − 末帧"，会被停顿前的静音带偏，**同一条素材符号相反**；
改成"末尾 0.3s 均值 − 开头 0.3s 均值"。
