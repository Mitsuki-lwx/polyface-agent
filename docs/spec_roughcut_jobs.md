# spec —— 粗剪任务化：异步任务 + 工作台入口

版本：2026-10-07　　对应 tasks：`docs/tasks_roughcut_jobs.md`　　验收：`docs/checklist_roughcut_jobs.md`

---

## 1. 背景

粗剪在命令行里跑通了（`docs/checklist_roughcut.md` 37/37），也**可见**了（阶段事件 + 进度 + 心跳）。
但它还是个 CLI，而工作台里**所有**操作都是同步 fetch + 一句状态文案 —— 这套东西撑不住分钟级任务。

具体地：25 秒素材 7 秒跑完看不出来；**5 分钟的口播光转写就约 60 秒**，
而 Java 调 Python 的短任务预算只有 60 秒 —— 必然超时，且前端只会显示"失败"。

## 2. 目标用户

作者本人（与 `docs/spec_roughcut.md` 一致）。**单机单用户**，不需要多租户、不需要分布式。

## 3. 能力清单（一句话一条）

1. 在**素材库里对某个视频**发起粗剪（一个按钮）
2. 发起时可以**改参数**（停顿阈值、字幕样式…）—— 复用已有的参数契约，不另造一套
3. 任务**在后台跑**，前端能持续看到**当前阶段 + 进度百分比**
4. 任务状态**可查询**，且**重启服务后不丢**（列表里还能看到上次跑到哪、成了还是败了）
5. 任务**可取消**（用户点了就走，不留孤儿进程）
6. 失败时能看出**失败在哪一步、为什么**（复用阶段事件里已有的信息）
7. 产物（成片 / 字幕 / 剪点）**自动进素材库**，不用用户自己去翻目录
8. 最近的粗剪任务**可列表**（谁、什么时候、成没成、产物在哪）

## 4. 非功能要求

- **不引入新依赖**（沿用"零新依赖"的既有姿态）
- **进度用轮询**，不引 SSE/WebSocket —— 单机单用户，轮询够用且最简单
- **观测不得影响业务**（沿用 `docs/spec_observability.md` 的硬不变量）
- **任务必须持久化**：进程重启后，状态与产物位置仍可查
- **不静默失败**：任务失败要留下可读的原因，且"看起来在跑其实早死了"必须能被识别
- **可关**：不想要这套的话，CLI 必须还能单独用（工作台不是唯一入口）

## 5. 设计骨架

**关键决定：Java 起子进程跑 CLI，事件文件就是两者之间的契约。**

```
工作台 ──► Java :8080 ──► 起子进程 ──► python scripts/roughcut.py 输入 --yes --events <路径>
              │                                    │
              │  读事件文件算进度 ◄─────────────────┘  写阶段事件（已有 schema，带 version）
              └── job 表（SQLite）记状态与产物
```

**为什么这么选**（对比"新开一个 Python 的 job API"）：

- 刚做完的阶段事件底座**正好就是现成的接口** —— 带 `version`、逐行 JSON、脱敏，
  本来就是按"给机器读"设计的；
- **Java 已经在管子进程**（gimpish serve 那套：启动/健康检查/退出清理），
  这套经验直接复用；
- **CLI 保持是唯一实现**：不会出现"命令行一套逻辑、服务里另一套"的分叉 ——
  这正是本项目反复吃亏的地方；
- 少一个 Python API 面 = 少一处要维护的契约。

**任务状态机**（最小集）：`排队 → 运行 → 成功 / 失败 / 已取消`

**进度的来源**：不是猜的，是**读事件文件**（阶段开始/结束 + 百分比）。
CLI 那边已经在写，这边只管读。

## 6. Out of Scope（本版不做）

- **把"生成稿件"也改成异步**（同样的病，但是另一件事）
- 分布式 / 多机 / 队列中间件
- **断点续跑**（本版从头跑；中断了重跑）
- 多任务并发调度（单机单用户，先串行）
- 任务重跑 / 定时任务 / 任务优先级
- 把 Langfuse trace 接到前端显示（可观测是开发期的事，不是本版的产品能力）
- 工作台里**预览**成片（先给"打开/下载"）
