# 真实作者验证方案（第三关）

日期：2026-09-16 · 状态：**可执行，待你找作者**
上游依据：`outputs/项目可行性与现实推进建议-2026-09-14.md`（第三关）· `docs/49` §8

---

## 1. 这个验证要回答的唯一问题

> **对一位真实创作者，polyface 产出的稿子，是否比"他平时用聊天 AI + 提示词"更省时间、更能直接发？**

不是问"功能是否实现"，也**不是**问"作者喜不喜欢"。只问上面这一句。

**为什么必须问真人**：目前全部证据（Python 180 / Java 43 项测试、端到端、浏览器实测）都是
**我们自己验自己**，且几乎全在 `LLM_MOCK=true` 下。没有一条证据能回答"它值不值得存在"。
`docs/38` §5、`docs/46` §6、`docs/48` §6 都显式标注了这个缺口。

---

## 2. 最小版本（先做这个，1 人 1 次，半天内可完成）

> 别等 5 个人。**1 位真实作者 + 2 份他自己的真实素材**就能暴露最大的问题；
> 最坏情况是发现"根本没用"——那也是最值钱的结论，因为省下了后面所有工程投入。

### 2.1 材料准备

| 项 | 要求 |
|---|---|
| 作者 | **不是你本人**；有真实发布习惯的创作者；日常已经在用聊天 AI 辅助写作（否则没有对照组） |
| 素材 | 该作者的 **2 份真实素材**（已发过的原创长文最好，300~2000 字） |
| 目标平台 | 该作者真正会发的平台（**不要为了测试逼他用不发的平台**） |

### 2.2 对照组设计（关键——没有对照就等于没测）

同一份素材、同一位作者，走两条路，**记录各自耗时**：

| 组 | 做法 |
|---|---|
| **对照组（他平时的做法）** | 作者用他惯用的聊天 AI + 自己的提示词，改出该平台可发布的稿子 |
| **实验组（polyface）** | 先用 polyface 生成，作者**在自己电脑上**逐字改到"我会发"的程度 |

**计时口径（必须一致）**：
- 两组都从"拿到素材"开始，到"**我认为可以发了**"为止
- 不计入工具安装/配置时间（那是另一回事，单独记）
- 改稿时间由作者自己掐表或用手机计时，**不要我们代记**

### 2.3 记录表（一位作者一张，直接填）

| 素材 | 组 | 到"可发布"耗时(分) | 是否真的发了 | 事实错误数 | 备注 |
|---|---|---|---|---|---|
| 素材1 | 对照组 | | | | |
| 素材1 | polyface | | | | |
| 素材2 | 对照组 | | | | |
| 素材2 | polyface | | | | |

**"事实错误数"怎么算**：作者逐句核对，凡出现「素材里没有的数字/时间/因果」「把素材的意思写歪」
都记一条。**这一项由作者判断，不由我们判断**——我们是利益相关方。

### 2.4 事后 3 个问题（口头答就行，别做大问卷）

1. polyface 的稿子里，**有没有哪一句是你自己想不到的**？（测"有没有增量"，不是测"像不像人写的"）
2. 你**下次还会用**吗？如果不会，最卡的是哪一步？
3. 如果它**只能保留一个功能**，你留哪个？

---

## 3. 判定门槛（先定，避免事后找理由）

| 结论 | 条件 |
|---|---|
| ✅ **值得继续投入** | polyface 组改稿时间 **明显少于**对照组（≥ 30%），且两份素材**都**没有"素材里没有的事实" |
| ⚠️ **需要修具体环节** | 时间优势不明显，但作者指出的是**可定位**的问题（如标题不好、语气不对、标签离谱） |
| ❌ **方向不成立** | 作者改稿时间 **不低于**对照组，或出现编造事实，或答"下次不用"且理由是产品性的（不是环境/安装问题） |

**注意 ⚠️**：若失败原因是"装不起来""跑不起来"，**不算方向不成立**——那属于 M5 交付问题（见 §5）。
必须把这两类原因分开记。

---

## 4. 执行步骤

1. 选定作者 → 说清"这是一次试用，不要求你发出来，只需要你如实说好不好用"
2. 让作者**在自己的电脑上**装发布包（`dist/polyface-0.4.0.zip`：解压 → `scripts\setup.bat` → `scripts\start.bat`）
   - **这一步本身就是 M5 的真机验证**——它同时补掉 `docs/48` §6 那个"批处理未实机执行"的缺口
   - 装不上就**原样记录报错窗口**，不要帮他绕过去（绕过去就测不出真实门槛）
3. 未配 LLM Key 时是 mock 模式 —— **必须显式告知作者**"这是模拟输出，只测流程不测质量"；
   要测质量**必须配真实 Key**（这一步顺带把"真实 LLM 模式未验证"也补了）
4. 按 §2.2 做两组，填 §2.3 表，答 §2.4 三问
5. 汇总 → 写进 `docs/` 交付说明；**无论结论好坏都如实记录**

## 5. 需要同时记录的"环境摩擦"（与产品判断分开）

这些不是产品问题，但会决定"别人能不能用上"：

| 项 | 记录什么 |
|---|---|
| 安装耗时 | 从解压到看到页面，多久 |
| 装不上的卡点 | 缺 Python / 缺 JDK / 端口占用 / 中文空格路径 / 杀软拦 |
| 首次配置难度 | 需不需要填 Key、填在哪、文档说清了吗 |
| 报错是否可自诊断 | `doctor.py` 的提示是否让作者自己解决了 |

---

## 6. 本方案自己批注的三个诚实边界

1. **样本量=1 不能证明市场**，只能证伪"完全没用"。要支持"值得投入"的判断，最终仍需
   `docs/06`/评估报告说的 5 位作者 —— 但**先做 1 位，成本低、能立刻砍掉明显不成立的方向**。
2. **作者可能是熟人，会客气**。所以 §2.4 第 2 问和第 3 问要**当面问**，并鼓励他说缺点；
   更硬的信号是 §2.3 的"是否真的发了"——**发了才算数**。
3. **真实 LLM 有额度与耗时问题**（单平台 60~250s、频繁 429，见 `docs/46`）。若作者用真实 Key，
   要提前说明"生成可能要等几分钟"，否则他会把等待算成产品缺陷——那其实是我们已知的额度问题。
