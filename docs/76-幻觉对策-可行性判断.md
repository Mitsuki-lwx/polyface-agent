# 幻觉对策 · 可行性判断（2026-10-09）

> **性质**：决策支持备忘，**不是** spec。目的是回答「值不值得投」，
> 以及「先投哪一条」。要开工仍需按项目规矩补三份文档。
>
> **上游证据**：`docs/checklist_eval.md` 的「实测」段（5 平台 × 10 条基线，通过率 52%）。

---

## 0. 先划清问题：我们面对的是哪一类幻觉

| 类型 | 表现 | RAG / 检索能治吗 |
|---|---|---|
| **知识缺口型** | 模型不知道 Notion 的用户数 | 能 |
| **越界推断型** | 素材说「要交286块」→ 写成「**漏交了**286块」；凭空加「半年数据」 | **不能**（素材全文已在 context 里） |

**基线实测：15 次 A7 失败全部是第二类。**

### 已排除的一个假设

我原本怀疑「事实清单有损（1334 字 → 只抽 10 条）导致 QA 误判」。**用基线数据验证后否掉了**：

```
素材里有、但事实清单里没有的短语  →  0 处
素材里也没有的短语（真幻觉）      →  23 处
```

结论：**QA 判得基本是对的**，问题不在"清单不全"，在"模型确实在编"。
（该检查用字面匹配，像「两百多个赞」这类改写的会漏判，所以是方向性证据而非精确统计。）

---

## 1. 候选方案与判断

### A. Extract-then-select（架构层，治本）

**做什么**：把「自由重写」换成「**从闭集里选**」。生成阶段不再让模型自由写事实，
而是先产出结构化骨架（每条事实 → 对应的平台化表述），正文由骨架组装。

**落点**：`DRAFT_SYSTEM` 与 `build_draft_prompt`（`app/pipeline/prompts.py`）。

**预期效果**：**结构性消除** A1（数字）与大部分 A7（新增断言）——
模型没有机会"顺口加一句"。这是唯一一条**从机制上**而不是"从提示上"治的路。

**代价**：改写质量可能下降（表达自由度变小）。**这是主要风险，必须实测。**

**可行性**：高。不引入新依赖，改的是 prompt 与产物结构。

---

### B. NLI 小模型做断言校验（校验层）

**做什么**：把成稿拆成原子句，逐句用 NLI（自然语言推理）模型判
「素材 ⟹ 该句」。比 LLM 判 LLM 更便宜、更稳、可复现。

**⚠️ 硬约束**：NLI 模型基本都要 **torch**，而本项目**明确排斥**它 ——
`faster-whisper` 就是因此没进默认依赖（数百 MB，违背"本地一键启动"）。

**可行路径**（按代价排序）：

| 路径 | 依赖体积 | 判断 |
|---|---|---|
| ONNX 量化版多语 NLI（`onnxruntime`，约 15MB + 模型 100~200MB） | 中 | **可行**，但要先验证中文效果 |
| API 侧做 NLI（用现有 LLM 的 embedding/分类接口） | 0 | 取决于服务商是否提供，未知 |
| 不引入模型，**扩展规则断言** | 0 | 最保守，但只能覆盖可机械判定的那部分（已在做） |

**可行性**：中。**必须先验证**「中文 + 素材⟹成稿」这个场景下小模型的判定质量，
否则会引入一类新的、更难排查的噪声。

---

### C. 加强现有 QA（最便宜，可立刻做）

**做什么**：两处小改

1. **QA 也拿到素材原文**（现在只给 3~10 条事实清单，`build_qa_prompt` 的 `facts`）
   —— 证据更多，判定更准
2. **定向重写**：现在 QA 不过会带 feedback 重写一轮。可以按**失败类型分路**
   （数字类 / 年份类 / 新增断言类），每条给不同的修复指令

**预期效果**：小。按 §0 的数据，QA 判得已经基本对；改它主要是**减少误判**，
不是减少幻觉。**不解决根本问题。**

**可行性**：高，改动小。

---

### D. 数字一律占位符回填（针对性）

**做什么**：正文里的数字/专名写成 `{{n1}}`，由代码从事实清单回填。
模型根本不接触数字。

**预期效果**：**直接消灭 A1 那一类**（基线里 5 次）。

**代价**：正文可读性/流畅度受影响（占位符会打断生成节奏），且模型可能不老实写占位符。

**可行性**：中高。可以和 A 合并（A 的骨架里本来就有"事实槽位"）。

---

## 2. 我的建议

**先做 A + D 的合并版**（骨架 = 事实槽位），理由：

1. 它是**唯一从机制上**堵住越界推断的路；B/C 都是"事后发现"，A 是"事前不可能发生"
2. 不引入新依赖，符合项目"本地一键启动"的底线
3. **可测量**：基线已经在了（A7 = 15、A1 = 5），改完跑一轮对比即可
4. `--reassert` 让"只改校验逻辑"的迭代只要 1.6 秒

**B（NLI）先不做**，但值得单独做一次**离线实验**验证中文效果 ——
如果效果好，它能替代"用 LLM 判 LLM"这个结构性弱点（裁判与被评同源）。

**C 顺手做**（QA 拿全文），成本极低。

---

## 3. 必须先回答的问题（答案会改变方案）

1. **改写质量与事实安全怎么权衡？** A 方案会牺牲一部分表达自由度。
   若你更看重"读起来像人写的"，A 要打折做（只约束数字与专名，不约束句式）。
2. **接受新依赖吗？** B 的 ONNX 路径会引入 `onnxruntime` + 一个 100~200MB 模型。
   不接受就只剩"规则断言"这条路。
3. **先在哪个平台试？** 基线里 bilibili 最差（30%，7 次失败 6 次是幻觉）、
   gzh 最好（80%）。在 bilibili 上试最容易看出效果，但样本噪声也最大。

---

## 4. 明确不做的

- **RAG / 检索**：素材全文已在 context 里，检索解决不了越界推断（§0）
- **DoLa / contrastive decoding**：需要模型内部 logits，走 API 拿不到
- **微调**：不在本项目能力与定位范围内
