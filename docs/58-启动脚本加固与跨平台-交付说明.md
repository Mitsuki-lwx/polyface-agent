## 4. `.sh` 全链路实机验证（本次最硬的一块）

**方法**：重新打发布包 → 解压到 **`D:\脚本 验证\r4\`（含中文与空格）** → 在该目录下跑脚本。
验的是"用户拿到的东西"，而不是源码目录。

**并且刻意在最恶劣条件下跑**：把 shell 环境里的 MSYS 路径自动转换**关掉**
（`MSYS_NO_PATHCONV=1` + `MSYS2_ARG_CONV_EXCL=*`，很多人为 docker/kubectl 会全局设）。
加固前这会让 venv 被静默建到 `D:\d\脚本 验证\...`；加固后一切正常。

```
D2  setup.sh         → venv + fastapi 0.141.1 / uvicorn 0.53.0 + .env ✓
                       且 D:\d 未被污染（证明 native_path 生效）
D3  start.sh         → python:18000 ✓  java:18080 ✓  就绪约 20s
D4  数据落点          → D:\脚本 验证\r4\polyface-0.4.0\data\polyface.db ✓ 包内
                       包外 D:\脚本 验证\r4\data\ 不存在 ✓
D5  /health          → 200 {"status":"ok","service":"polyface-backend","mock":true}
    /api/platforms   → 200，5 个平台（xhs/douyin/gzh/zhihu/bilibili）
    端到端生成        → materials → generate(xhs) → status=qa_passed，正文 175 字
D6  stop.sh          → 只结束 java/python；[已释放] 18080 / 18000 ✓
D7  二次 start.sh    → 同端口再起；数据仍在（2 素材 / 2 稿，正文完好）✓
```

**反证**：同一台机器、同一个 jar，**裸 `java -jar polyface.jar`（不设 `POLYFACE_DATA_DIR`）**
会把 `polyface.db` 写到**包外的上级目录** —— 日志原文：
`SQLite store: D:\脚本 验证\r2\polyface-0.4.0\..\data\polyface.db`。
根因是 `Store.java:73` 的默认值 `../data` 相对**启动时的当前目录**。
设置 `POLYFACE_DATA_DIR` 后：`...\r4\polyface-0.4.0\data\polyface.db` ✓ 落在包内。
**这条对照实验正是本次要证的东西：脚本不是装饰，它挡住了一个真实的静默故障。**

> `D5` 是 `used_mock=true`（离线演示模式）—— 隔离目录里没有 API Key，这是**正确行为**。
> 真实模型的端到端证据见 `docs/54`（14/14，`glm-5.2`），本次未重复（额度有限）。

## 8. 一个必须说清楚的坑（环境相关，但会骗人）

**`env -u PYTHONPATH -u PYTHONSTARTUP -u PYTHONHOME <python>` 在本机会静默丢掉全部输出**：
退出码 `rc=0`、stdout 0 字节。裸调用（不加 `env -u`）正常。

这个假象在本次排查中**两次把结论带偏**（"脚本没输出"、"没建任何东西"）。
真正的原因是 `PYTHONHOME` 被 `env -u` 移除后解释器 stdio 行为异常，
而 `PYTHONHOME` 在本机**本来就是未设置的** —— 也就是说 `-u` 是多余的，
它不是在"清理环境"，而是在**破坏解释器**。

> **教训**：先前笔记里"实跑 `.sh` 需要 `env -u PYTHONPATH -u PYTHONSTARTUP -u PYTHONHOME`
> 规避 Python shim 注入"这条经验**是错的，已作废**。本机可以裸 `bash scripts/setup.sh`。
> 已同步修正 `MEMORY.md`。
