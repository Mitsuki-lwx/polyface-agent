## 3. 发现并修复的缺陷 F-1（阻塞性）

**现象**：`python scripts/build_release.py`（完整构建）在 Windows 上**必然失败**：

```
      Maven 命令：bash D:\media works move\polyface\scripts\mvn.sh
/bin/bash: D:\media works move\polyface\scripts\mvn.sh: No such file or directory
[失败] Maven 构建失败（退出码 127）
```

**根因是两层叠加的**（第一层修完仍然失败，是**实测断言**把它抓出来的）：

| 层 | 问题 | 修法 |
|---|---|---|
| ① | 把 **Windows 路径** `D:\...` 喂给 bash | 改 `wrapper.as_posix()` → `D:/...` |
| ② | 用**裸 `"bash"`** —— 交给 CreateProcess 解析时，`System32\bash.exe`（**WSL bash**）会先被命中。那是另一个文件系统视图：看不到 `D:/...`，还会**吃掉路径里的反斜杠** | 改 `shutil.which("bash")` 的**绝对路径**（PortableGit bash，才有 D: 盘视图） |

②的实测证据（这才是只改①不够的原因）：
```
bare 'bash'                          → rc=127  /bin/bash: C:UserslwxAppDataLocalTemp...: No such file or directory
shutil.which('bash') 全路径 + D:/…   → rc=0    /d 存在（MSYS 视图）
```
注意反斜杠被吃掉了 —— 这是 WSL bash 的典型行为，也是原报错原文的由来。

**为何一直没被发现**：09-20 那次打包走的是 `--no-build`（复用既有 jar），
**从未触发 `build_jar()`**；而 `docs/48 §7` 第一条推荐命令恰恰是完整构建。

**归属**：**包组装缺陷**（工具链自身），不影响运行时。
与 09-20 给 `.sh` 修的 MSYS 路径问题是**同一类**，只是方向相反
（那边是"给原生程序 POSIX→Windows"，这里是"给 bash 程序 Windows→POSIX"），**没修到 `build_release.py`**。

**回归防线**（3 项，其中第 3 项最关键）：

| 测试 | 断言 |
|---|---|
| `test_maven_cmd_uses_which_bash_not_bare_name` | 必须是 `which("bash")` 的绝对路径（裸名会落到 WSL bash） |
| `test_maven_cmd_gives_bash_a_posix_path` | 路径不含反斜杠 |
| `test_maven_cmd_path_is_actually_resolvable_by_bash` | **让即将被执行的同一个 bash 亲自 `test -f`** —— 前两条只检查"命令长什么样"，这条才证明"真能跑"，正是它抓出了第二层 |

**变异测试**：还原成 `str(wrapper)` → 两项变红；还原成裸 `"bash"` → 对应项变红。均已还原并核对。

## 4. 观察（**不是缺陷**，如实记录）

| 观察 | 判定 | 说明 |
|---|---|---|
| `setup.sh` 打印「启动前体检」后**无输出** | ✅ 正常行为 | 它用的是 `doctor.py --quiet`；全部通过时静默是预期语义。已实测：`--quiet` 只压 OK 行，**仍会打印阻塞项与指引**，且阻塞时**退出码 1** —— 所以 `setup.sh` 的 guard 有效。**唯一的 UX 小瑕疵**：打印了段落标题却没有内容，用户可能以为坏了。建议以后给 `--quiet` 通过时补一行 `[OK] 体检通过` |
| `stop.sh` **没有非交互开关** | ⚠️ **可用性缺口（非阻塞）** | `read -r -t 60` 硬编码确认；非交互调用会**卡满 60 秒后取消**。交互确认本身是合理设计（`docs/58` 记录过本机 8000 被第三方占用），缺的是 `-y` 之类入口。本次**按 `docs/60 §6` 的 Out 范围不顺手改**，列为跟进项 |
| `make_zip` 先 `unlink` 旧 zip | ⚠️ 环境限制 | 我的沙箱拦截了该删除（`SAFE_DELETE_FAIL_CLOSED`），导致覆盖打包失败；手工删掉旧 zip 后正常。**正常环境无影响**（`ZipFile(mode="w")` 本就会截断，那个 `unlink` 是冗余的）。不视为缺陷 |
