## 1. 默认值表（**每一项都必须能被覆盖**）

| 项 | 默认值 | 覆盖方式 | 说明 |
|---|---|---|---|
| 对齐策略 | `voice_first`（配音优先） | 命令行 / 接口 / UI | spec 关键决定二 |
| 转场时长 | 0.4s | 命令行 / 接口 / UI | 太长会显得拖沓 |
| 缓动强度 | 1.08（放大到 108%） | 命令行 / 接口 / UI | 1.0 = 静止（那就退化成轮播了） |
| BGM 音量 | -18 dB（相对配音） | 命令行 / 接口 / UI | 配音必须听得清 |
| BGM 淡出 | 1.5s | 命令行 / 接口 / UI | |
| 节拍容差 | 0.12s | 命令行 / 接口 | 判定"落在节拍上"的窗口 |
| 字幕字号/颜色/边距 | 沿用 `RoughcutParams` 同名字段 | 命令行 / 接口 / UI | 与粗剪一致，别立第二套 |
| 配音缺失时 | 降级为无声 + 字幕 | 不可配（行为） | **绝不因缺依赖而整体失败** |
| librosa 缺失时 | 跳过卡点并**说明未做** | 不可配（行为） | |

**验收**：每行在 §2 里有对应观测（不可配的项 → 变异测试）。

## 2. 参数与常量（改了行为要变）

- [x] 缓动强度改成 `1.0` → 画面**接近静止**（2026-10-26 实测）
      **判据改过** ✗：原文要求"抽首尾帧**相同**"，而 H.264 是**有损**编码，
      同一静止画面两次解码也不会逐位相同 —— 该判据**不可能满足**。
      改成量 **PSNR**：镜1 内 2s vs 10s，`zoom=1.0` → **39.46 dB**（几乎一样），
      `zoom=1.08` → **15.63 dB**（差别巨大，真的在推近），同一文件自比 = `inf`（上限）。
- [x] 转场时长 0.4 → 1.2 → **画面段的转场长度变化**（2026-10-26 实测）
      **断言写反了** ✗：原文说"成片总时长相应变化"，而 `video.segment_durations` 的注释写明
      「每段多给一个转场时长，重叠之后**总长正好 = 配音总长**」——
      **总时长对转场是不变量，这是故意的**（否则越往后字幕越错位）。
      实测：0.4 → 99.760s、1.2 → 99.760s，帧数都是 2494（**完全相同** ✓ 符合设计）。
- [x] BGM 音量改成 `-60` → 成片里 BGM 几乎听不到（2026-10-26 实测）
      **断言写反了** ✗：原文说"改成 `0` → 听不到"，而 **0 dB 是最响**（默认是 -18 dB）。
      实测 `volumedetect` 的 mean：-18 dB → **-21.7**、0 dB → **-10.4**（明显更响）、
      -60 dB → **-23.3**。可见"改小 → 更安静"成立；"0 → 听不到"不成立。
- [x] 节拍容差改成 `0.001` → 记录里"落在容差内的边界占比"**明显下降**（2026-10-26 实测）
      实测：容差 0.12 → 对齐 **64%**；容差 0.001 → 对齐 **9%** ✓（说明它确实是算出来的）

- [x] 每个分镜的时长 == 该分镜配音的**实际时长**（不是 `duration_hint`）

      seq 1  plan=19.658  wav=19.658 ✓   seq 7  plan= 8.806  wav= 8.806 ✓

      seq 3  plan=13.404  wav=13.404 ✓   seq10  plan= 7.721  wav= 7.721 ✓
      …                                  seq11  plan=12.510  wav=12.510 ✓

      **11/11 分毫不差**（差 < 0.06s）✓。
- [x] `duration_hint` 与配音长度**明显不符**时，以**配音**为准（构造一个刻意不符的分镜验证）

- [x] 分镜顺序 == 剪辑单顺序（不重排）

## 5. 画面与转场

- [x] 每个分镜的画面是**用户选的那张图**（不是随机图、不是占位图）
      **实测**：把记录里每个分镜的 `image` 哈希与素材库 `asset` 对账，**11/11 全部对得回上传的资产** ✓
      （`seq1 → #25 分镜10配图`、`seq3 → #18 分镜3配图` …）。
      e2e 脚本的图是循环取样的，所以有重复用图 —— 那是**测试夹具**的事，不是产品行为。
- [x] 画面**在动**：抽同一分镜的首帧与尾帧，**必须不同**
      **实测（2026-10-28，量 PSNR —— H.264 有损，逐位相同不可能，见 §2 那条判据的更正）**：
      ```
      scene-001  首尾帧 PSNR = 15.06 dB
      scene-005  首尾帧 PSNR = 18.90 dB     （静止画面该接近 40 dB，见 §2 的 39.46 dB 对照）
      scene-008  首尾帧 PSNR = 12.50 dB
      ```
      → 都在**真的推近/平移** ✓。
- [x] 分镜之间**不是硬切**：抽转场中间帧，能看到两图混合
      **实测（第 1/2 镜分界 t=19.658s、转场 0.4s）**：
      ```
      PSNR(转场中点, 第1镜) = 14.12 dB
      PSNR(转场中点, 第2镜) = 12.28 dB
      PSNR(第1镜,   第2镜) =  9.58 dB   ← 两图互差（基线）
      ```
      中点到**两图都比两图互差更近** → 是**混合**✓。硬切的话中点会与其中一图**逐位相同**（PSNR=inf）。
- [x] 缺图的分镜 → **明确指出是第几个**，不静默用占位图
      **两条防线，都实测过**：
      - **前端（发起前就拦）**：`index.html:1784` → `❌ 第 ${missing.join("、")} 个分镜还没选图` ✓
      - **后端（真拦得住）**：e2e 故意少给一张 →
        `HTTP 400 图片数量与分镜数对不上：分镜 11 个，给了 10 张` ✓；
        给 `null` 占位时更精确：`第 [2] 个分镜没有可用的图片（图片必须是素材库里的图）` ✓
      **绝不静默用占位图** ✓（400 直接拒，不往下跑）。

## 6. BGM 与卡点（两种策略必须真的不同）

- [x] `voice_first`：**分镜时长与 §4 完全一致**（配音没被改）
      **实测**：`voice_first` 的 `scenes[].seconds` 就是 §4 那串配音实际时长
      `[19.658, 17.983, 13.404, 5.458, 18.218, 17.263, 8.806, 21.275, 10.456, 7.721, 12.51]` ✓
      —— 只**平移 BGM 起点**，不动分镜。
- [x] `voice_first`：记录里有 BGM 偏移量，且偏移是**为了让更多边界落在节拍上**算出来的
      **实测**：`bgm_offset_sec = -0.107`（正偏移已按语义换算成"跳过 BGM 开头"），
      同一份记录里 `aligned_ratio_before_offset = 45%` → `aligned_ratio = 55%` ✓
      —— **偏移之后对齐率确实上升**，证明这个偏移是**搜出来的**，不是随便给的常数。
- [x] `beat_first`：分镜边界**落在节拍容差内**的占比**明显高于** `voice_first`
      **实测（同素材、同图、同 BGM，只换策略）**：`voice_first` **55%** → `beat_first` **91%** ✓
      （另一次跑：64% → 91%）。
- [x] `beat_first`：允许分镜时长与配音长度**不一致**（记录里要能看出来）
      **实测（逐分镜对比两种策略）**：
      ```
      seq 4  voice_first= 5.458   beat_first= 5.340      seq 6  voice_first=17.263  beat_first=17.322
      seq 9  voice_first=10.456   beat_first=10.658      seq 1  voice_first=19.658  beat_first=19.551
      ```
      **11/11 个分镜的时长都被动过** ✓（`beat_first` 就是靠这个换踩点）。
      这就是它的代价，spec §7 里如实写了。
- [x] 记录里的"落在节拍容差内的边界占比"是**算出来的真值**（改容差它会变，见 §2）
      **实测**：容差 `0.12` → 64%/91%；容差 `0.001` → **9%** ✓（§2 那条）。
      另外补了一条：**没测的时候记 `null` 而不是 `0.0`**（见 §3 与本节末尾）。
- [x] BGM 结尾有淡出
      **实测（成片最后 3 秒的 RMS 包络）**：`-45.2 → -46.3 → -46.0 → -46.2 → -47.9 → -50.4 → -55.4 → -61.7 dB`
      —— **单调下坠到 -61.7 dB** ✓（默认 `--bgm-fade-out 1.5`）。

### 缺陷 1：TTS 插件**写失败绕过了重开重试**（真链路 11 个分镜丢 3 个旁白）

**症状**：一次成片 11 个分镜里 **3 个（4/6/9）配音失败**，被静音垫片顶住 ——
成片时长保住了（记录与成片分毫不差 ✓），**但旁白就是没有**。
另一次跑同一个脚本 **0/11 失败** → **间歇性**。

**根因（代码级，不是猜的）**：`windows-sapi` 是**一问一答型**插件（读一行、合成、退出），
所以存在"插件正在退出、但 `alive()` 还说活着"的窗口。往那种进程写 stdin 会抛
`[Errno 22] Invalid argument`。而 `_once()` 把它包成了 `PluginError`（`RuntimeError`）——
`call()` 里那句"进程死了会自动重开一次"的 `except (BrokenPipeError, OSError)` **根本接不到** ✗
→ **本该重开重试的失败，直接变成整镜配音失败**。

**同一条路上还有第二个洞**：`_spawn()` 重开后，**旧进程的读线程往"当前队列"里塞**，
于是新请求会读到**旧进程的回复**。做了确定性复现（请求 `DDD`，拿到旧进程的 `CCC`）——
**一个静默的错误结果**，比报错危险得多。

**修法**（`python-service/app/pipeline/tts_plugin.py`）：
- `_once()` 的写失败改抛 `BrokenPipeError`（是 `OSError`）→ 走回"重开重试"那条路
- `_spawn()` 把队列与 stderr 尾巴**当参数**传给读线程 → 队列与进程**成对**

**验证**：两条回归测试（`test_write_failure_is_retried_not_fatal` /
`test_respawn_does_not_leak_old_process_replies`）都做了**变异测试**：
改回旧行为 → **变红**（红出来的正是真机上那个 `[Errno 22]`）。
真链路复跑：**`tts.failed` 从 3/11 → 0/11**，两次都干净 ✓。

### 缺陷 2：成片产物**血缘没挂**（`asset_link` 一行都不写）

`registerFilmOutputs` 只在"输入本身就是资产"时才建链；图文成片的输入是**剪辑单**（从成稿里取的），

### 缺陷 3：字幕里的键帽**渲染成豆腐块**

抽帧核对成片时看到 `□压缩固定开支` ✗ —— 成稿里的 `1️⃣2️⃣3️⃣4️⃣5️⃣` 全烧成了方块
（这份稿 11 条字幕里占 **5 条**）。

**排查**（受控实验，不是猜）：
| 变体 | 结果 |
|---|---|
| 现状（`Microsoft YaHei`） | `□压缩固定开支` ✗ |
| 换 `Segoe UI Emoji` | **还是方块** ✗（换字体治不了） |
| `fontsdir` | 滤镜串被 Windows 盘符切碎（已知坑，见 `_subtitle_vf` 注释） |
| **剥掉组合符** | `2 压缩固定开支` ✓ |

普通 emoji（📊 ✅ ✨ 🔥）靠字体回退**能**画出来，所以**只剥**键帽的组合符
（`U+FE0F` / `U+20E3`）、**数字留住**。落点在 `rc.segments_to_srt`（粗剪与图文成片**共用的唯一出口**）。

## 附带修掉：**中文配音全是乱码**（2026-10-30 才发现，影响本文件的全部"有配音"结论）

> 这一条是验 `checklist_scene_split`/`disfluency` 时**顺带**用 ASR 回读发现的 ——
> 它不属于 b1 的判据，但它让 b1 产出的**每一条中文旁白都是废话** ✗。

**症状**：`tts.synthesize("大家好，我是巳月。")` 出来的 WAV，**时长合理、格式正确**
（22050/16bit/单声道），但用 ASR 转回来是「蟬蓮金任錫假意沉重鬼末」✗。
英文**完全正常** ✓ —— 所以只有真人一听才发现，机器量"有声、时长对"永远发现不了 ✗✗。

**根因**：`_PS_TEMPLATE` 里 `$synth.Speak([Console]::In.ReadToEnd())` ——
`[Console]::In` 按**控制台代码页**（本机 936/GBK）解 stdin，而 Python 写进去的是 **UTF-8** ✗。
ASCII 两种编码一样，所以英文不受影响 ✓。

**修法**：显式按 UTF-8 读 stdin（`StreamReader([Console]::OpenStandardInput(), UTF8Encoding)`），
不依赖控制台代码页 ✓。

**验证**：`test_chinese_text_reaches_sapi_uncorrupted`（合成 → ASR 回读 → 关键词必须在）——
变异（改回 `[Console]::In`）→ **变红**，红出来的正是那段乱码 ✓。
修复后长句**逐字正确**（"今天聊聊怎么把一篇长文改成五个平台的稿件。" → 一模一样），
同一句的时长还从 3.54s 变成 **2.74s**（乱码时更长，又一佐证）。

**对本文件的影响**：§4（分镜时长 == 配音实际时长）✓、§6（BGM 淡出）✓ 这些**判据本身仍然成立**
（时长与音频都合法）；但"**旁白内容**"是这一轮才变正确的。
本文件里 2026-10-28 那几次成片的旁白，**当时是乱码** ✗（如实补记）。
