## 2. 修复的五个缺陷

| # | 缺陷（评估报告指出） | 修复 |
|---|---|---|
| 1 | Java 调 Python 读超时**固定 180 秒** | 拆成**双客户端**：短任务 60s / 生成 240s，均可配（`polyface.llm.timeout-sec`） |
| 2 | 真实单平台曾耗时 **250 秒**，会先撞 180s 超时 | 生成走独立长超时预算；默认值 240s 留余量，**不设无限** |
| 3 | Java **等全部平台返回才落库** | 改为**部分落库**：成功平台照常入库，失败不阻塞 |
| 4 | Python 串行阶段异常**直接上抛**，丢掉前面平台成果 | 逐平台容错：失败记入 `failures`，其余照常返回 |
| 5 | 前端只有一个笼统结果 / 502 | 显示「成功 X / 失败 Y」+ 失败平台与原因 + **「重试失败平台」**；默认单平台 |

**本质**：把「多平台批量生成」从**原子操作**改成**可部分成功**的操作。

## 4. 关键设计决策

| 决策 | 理由 |
|---|---|
| **超时拆成双客户端**，而非调大单一超时 | 短任务（解析/学习/用量）本就该快失败；共用一个 240s 会让「解析卡住」也白等 4 分钟 |
| **默认 240s，且默认单平台** | 240s 对实测 250s 上限留余量；**不设无限超时** —— 无限超时只是把问题推给用户 |
| **非法平台提前 400，不进生成循环** | 平台校验在 Python 侧 `ValueError` → 400；Java 侧把 4xx **原样透传**，不包装成 502（502 会让用户以为服务坏了） |
| **失败记 `failures` 且**不静默 | `logger.exception` + 响应带平台与异常类型；避免「逐平台容错掩盖系统性问题」 |
| **容错只包在单平台调用外层** | 不动 `_generate_one` 内部逻辑，既有测试语义不变 |
| **Java 超时 → 明确「未完成」** | 不谎报成功；错误文案给出可操作建议（重试 / 减少平台数） |
| **不做后台队列 / 异步轮询** | 评估明确「不需要立刻上」；部分成功保留成本低、收益大 |

## 5. 过程中发现并修复的问题（浏览器实测暴露）

| # | 问题 | 怎么发现的 | 影响 |
|---|---|---|---|
| 1 | 默认勾选的平台**没有高亮样式** | 浏览器实测 E1b 断言 `label.classList.contains('checked')` 为 false | `input.checked = true` 程序化赋值**不触发 `change` 事件**，label 拿不到 `.checked` 类 → 用户看不出默认选中哪个平台（功能对、视觉不对）。已手动同步类名 |
| 2 | E6 断言一度超时 | 诊断输出显示 `disabled: True` | **不是缺陷**：重试生成期间按钮被禁用（防重复提交），测试脚本没等重试那一轮结束就点下一次。修正测试脚本，非产品代码 |

第 1 项值得记：**纯功能断言（checked == 1）会漏掉它** —— 是「样式与状态是否一致」这类断言才暴露出来。
