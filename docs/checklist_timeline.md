## 5. 重渲染

- [x] 从源视频重剪（**不是**从旧成片剪）—— 证据：日志里 ffmpeg 的输入是源文件
      （实测 `stderr.log`：「源：…\assets\a4\a4832a2a….mp4」✓，
      workdir 里有 `work/cut.mp4` + `work/done/stage-剪裁.json` ✓）
- [x] 产出新成片，**不覆盖**源视频与旧成片
      （源视频 mtime **10-18 16:57**、旧成片 `out.mp4` mtime **10-18 16:58**，都没动 ✓；
      本次产出是**新文件** `render.mp4` ✓）
- [x] 成片时长 == `keep` 推出的总长（容差内）
      （`render.mp4` = **11.760s**，`keep` 总长 = **11.815s**，差 **0.055s** < 0.2s ✓）
- [x] 字幕用的是时间线里的 `segments`（改一条字幕 → 成片里真的变了）
      （实测：把第 1 条字幕前面加 `【字幕改了-验证用】` → `PUT /api/timelines/12` 保存 →
      重渲染 job 10 → **srt 里有该标记** ✓，且**画面也变了**：
      帧@4s 的 md5 `45ec7ed45e` → **`14bf66f3bd`** ✓
      （对照：源图无字幕是 `68d30aef04`））
      ⚠️ 参数结构要注意：`segments` 在 **`timeline` 体内**（`GET` 返回 `{asset_id,…,timeline:{keep,segments,source,version}}`），
      我第一次改的是顶层 `segments`（空数组），保存成了空操作 ✗。
- [x] 重渲染是**任务**：能看到进度、能取消
      **实测通过（2026-10-27），但过程中发现并修掉一个真 bug** ✗：

      **进度** ✓：任务对象带 `progress`，轮询能看到阶段递进 ——
      `{'stage': ''}` → `{'stage': '探测'}` → `{'stage': '剪裁', done_stages: ['探测'], last_message: '720×1280，24.84…'}`
      → `{'stage': '烧字幕', pct: 100.0}` → `succeeded` ✓。

      **取消** ✗→✓：**原来对刚发起的任务不生效** ✗。根因是竞态 ——
      `RoughcutRunner.execute` 里 `store.markJobRunning()` 在 `pb.start()` **之前**、
      `running.put()` **之前**，中间有窗口：状态已是 `running`、进程还没登记。
      那一刻调 `cancel()` → `running.get()` 拿不到进程 → `killed=false`；
      而 `abandoned` 只认 `interrupted` → 也是 false → 回 `{"canceled": false}`，
      **任务照跑到底** ✗（实测：发起渲染后立刻取消，两个 job 都变成 `succeeded`）。

      **修法**（两处）：
      1. `JobController.cancel`：把 `queued`/`running` 也认作"可放弃"（原本只认 `interrupted`）；
      2. `RoughcutRunner.execute`：`running.put()` 之后**补一次取消检查** ——
         若期间已被标 canceled，立刻 `destroyForcibly()` 并如实收尾。

      **修后实测**：
      ```
      delay=0.0s → {"canceled": true, "status": "canceled"}  最终 canceled ✓
      delay=0.5s → {"canceled": true, "status": "canceled"}  最终 canceled ✓
      ```
      Java 单测 **132 passed** ✓ 无回归。
- [x] 重渲染任务**能断点续跑**（杀掉重启 → `interrupted`）
      **实测通过（2026-10-27）**：
      1. 发起重渲染（job 16）→ `sleep 0.3` → `Stop-Process -Force` 杀掉 Java；
      2. 杀完库里 job 16 仍是 **`running`**（正是那个"永远不会动的进度条"状态 ✗）；
      3. 重启 Java → 启动清理（`RoughcutRunner.recoverInterrupted`）把它标成
         **`interrupted`**，`error = "服务重启时任务尚未结束（可继续）"`，API 里 **`can_resume: True`** ✓。

      **为什么是 `interrupted` 而不是 `failed`** ✓（代码注释写明）：粗剪的中间产物本来就落盘保留，
      用户点一下就能从断掉的阶段接着跑；标 failed 会让它从"可继续"里消失 ✗。

## 6. 字幕跟剪点走（**本模块最容易错的地方**）

- [x] 删掉中间一段 → **落在该段内的字幕整条消失**
      （实测：源字幕 `B[6,8]` 落在删除段 [5,10) 内 → 输出里**没有它** ✓；
      尾部删除段里的 `E[16,18]` 同样消失 ✓）
- [x] 跨删除边界的字幕 → **被截断**（不是整条丢、也不是错位保留）
      （实测：源 `C[4,12]`、keep=`[[0,5],[10,15]]` → 输出 **`[4.000, 7.000]`** ✓。
      换算：`4` 本来就在保留段 [0,5] 里（**不需要 clamp**）、`12` 在 [10,15] 里；
      `film(4)=4`、`film(12)=5+(12-10)=7` → 源里 8s 的字幕在成片里是 **3s** ✓ 正是"截断"。
      ⚠️ 我第一次把期望写成 `[5,7]`（误以为起点也要 clamp）—— **是我错，实现对** ✗）
- [x] 删完之后逐段抽查：**字幕与画面对得上**（时间轴换算到成片时间）
      （实测：`A[1,3]` 落在第一个保留段内 → 成片里仍是 `[1.000, 3.000]` ✓；
      且函数设计上"**一个条目不拆**"—— 成片连续，所以源区间映射后仍是**一段连续时间** ✓）
- [x] 只改一段的结尾 → **别的段落的字幕不受影响**
      （实测：keep 第二段结尾 `15 → 13`：第一段里的 `A` 输出**逐字节不变** ✓；
      第二段里的 `D` 由 `[6,9]` → `[6,8]` ✓ 受影响且只受它该受的）

- **没做拖拽时间轴** —— 第一版是表格 + 预览帧（理由见 spec 关键决定二：先验证"改数据"好不好用）
- **没做导出剪映/FCPXML/EDL** —— 先做自己闭环，互通是下一期
- 没做分镜/镜头切分/音轨/转场/变速
- **没做撤销/版本历史** —— 改坏了可以从粗剪重来（时间线是派生数据，重跑粗剪就有新的）
- 时间线**不存 ffmpeg 参数**（渲染细节不进数据格式）
- 重渲染**从源重剪**的代价是**慢**（分钟级）—— 换来的是不叠加压缩损失、改字幕真的生效
- **字幕"是否错位"只做了程序化核对**（该消失的消失、其余恰好一次、时间轴换算对）
  —— **没有人工看片逐段确认**画面与字幕的对应
- 端到端用的是 `make_fixture.py` 造的 24.84s 素材（Windows TTS），不是真人录制
- 预览帧用的是 `<video>` seek（每行一个视频元素）—— 行数多时（比如几十段）会偏重，
  本版没做虚拟滚动/懒加载
- `segments_to_source` 在**边界**上的取整用的是"起点贴左、终点贴右"；
  更精细的语义（比如按语音活动对齐）没做

## 顺带修掉的（实测才发现的，都不是本模块新写的）

| 问题 | 现象 | 根因 |
|---|---|---|
| 字幕**重复 + 28ms 碎片** | 同一句出现两次，其中一段只有 28 毫秒 | `segments_to_film` 按保留区间**拆**字幕 —— 但成片是**连续的**，源区间映射过去本来就该是一个条目 |
| `/api/timelines` 列出 **srt** | 时间线列表里混进 `render.srt`，`GET` 它还把字幕文本当 JSON 解 | `timeline` 在资产模型里是**类**（json/srt/vtt/ass 都归它），只判 kind 不够 |
| **预览帧全空** | `<video>` `readyState=0`，不出画面 | 媒体托管路径是 `/api/media/**`，代码里拼了 `/media/` → 404 |

第三条正是**浏览器实测**才揪出来的 —— 接口返回 200、时长也对，光看接口发现不了。
