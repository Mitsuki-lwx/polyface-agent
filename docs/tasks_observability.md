# tasks —— 运行透明化：阶段事件 + 进度可见 + 参数可问

版本：2026-10-06　　方案：`docs/spec_observability.md`　　验收：`docs/checklist_observability.md`

---

> 每个任务能在一次专注会话内做完。顺序即依赖顺序。
> 「参考资料定位」给到文件/函数，实现时直接去读，不要凭记忆写。

---

## T1 · 定下阶段事件的形状

- **做什么**：定义"一条阶段事件"有哪些字段、有哪些事件类型、文件怎么放、版本号怎么带
- **影响文件**：新模块（建议 `python-service/app/pipeline/runlog.py`）
- **依赖**：无
- **参考资料**：
  - 项目既有的本地 JSONL 姿态：`python-service/app/usage.py`（脱敏、只记长度/计数、失败只告警）
  - 既有的 trace 思路：`python-service/app/trace.py`、`observability.py`（trace_id 贯穿）
  - ⚠️ **要吸取的教训**：`docs/29` 记过"观测破坏业务语义"（上下文管理器重复 yield 导致异常被替换）。
    ⇒ 上报必须包在 try/except 里，**任何上报失败都不得影响业务**
- **完成判据**：字段清单写死在代码里（常量），有 `version`；一条事件能序列化成一行 JSON 且可反解

## T2 · 事件流：落盘 + 终端渲染两个消费者

- **做什么**：一个最小的发布/订阅：业务发事件 → ①写文件 ②渲染到终端
- **影响文件**：同上模块
- **依赖**：T1
- **参考资料**：无
- **完成判据**：
  - 关掉文件输出时**不创建文件**；关掉终端输出时**不打印**
  - 写文件失败（如目录不可写）**只告警**，业务继续跑完

## T3 · 输出分级与"重要的行"

- **做什么**：三档输出（安静/正常/详细）；"正常"档要有**心跳**（长阶段不至于看起来卡死）
- **影响文件**：同上模块
- **依赖**：T2
- **参考资料**：无
- **完成判据**：
  - 安静档只出最终结果与错误
  - 详细档才把底层工具的原样输出流出来
  - 一个"故意很慢"的假阶段，在正常档下**每 N 秒有一行心跳**

## T4 · 阶段埋点：把粗剪的各步接上事件

- **做什么**：探测 / 找停顿 / 剪 / 转写 / 出字幕 / 烧字幕 各发开始-结束事件（带耗时与结果计数）
- **影响文件**：`python-service/app/pipeline/roughcut.py`、`scripts/roughcut.py`
- **依赖**：T2
- **参考资料**：
  - 现有各步函数在 `roughcut.py`：`probe` / `detect_pauses` / `cut_video` / `extract_wav` /
    `burn_subtitles` / `preview_frame`；ASR 在 `asr.py::transcribe_segments`
  - ⚠️ 当前 `_run()` 用了 `capture_output=True`，**底层输出被吞掉** —— 这正是"黑盒"的根因
- **完成判据**：跑一次粗剪，终端能看到**每个阶段各一行**（名字 + 耗时）；事件文件里能对上

## T5 · 细粒度进度：转写与渲染

- **做什么**：解析底层工具已有的进度输出，换算成百分比上报
- **影响文件**：同上模块
- **依赖**：T4
- **参考资料**：
  - ffmpeg 的进度可用 `-progress` 输出成机器可读的键值行（比解析人读的 stderr 稳）
  - 转写侧：faster-whisper 的 `segments` 是**生成器**，边出边报即可（用音频总时长换算百分比）
  - 实测参考：本机 ASR 约 0.21x 实时，25s 素材转写约 5s
- **完成判据**：正常档下，转写与渲染阶段能看到**百分比变化**（不是只有开始/结束两行）

## T6 · 运行报告

- **做什么**：结束后输出一份汇总：每步耗时 / 本次生效参数 / 剪点 / 产物位置（成片、字幕、剪点文件、中间件目录）
- **影响文件**：`scripts/roughcut.py`
- **依赖**：T4
- **参考资料**：现有 `roughcut.summarize()` 已给"剪点 + 参数"，本次是**加上耗时与产物路径**
- **完成判据**：报告里的路径**真的存在**；每步耗时与事件文件里的一致

## T7 · 参数可问：把"展示 + 接受修改"做成一个小循环

- **做什么**：开始前展示**本次生效的全部参数**（标注来源：默认 / 配置文件 / 命令行），
  允许当场改；问哪些、问不问由配置决定
- **影响文件**：`scripts/roughcut.py`（复用 `RoughcutParams`，**不要另造一套**）
- **依赖**：无（可与 T1–T6 并行）
- **参考资料**：
  - 现有交互在 `scripts/roughcut.py` 的 `ask()` 与那个 `while True` 预览循环
  - 参数契约在 `roughcut.py::RoughcutParams`（`load()` / `merged()` / `describe()`）
  - ⚠️ 既有教训：`docs/62` §4 记过 `stop.sh` 因"没有非交互开关"被记为可用性缺口
    ⇒ **必须同时留非交互开关**
  - ⚠️ 既有教训：`sys.stdin.isatty()` 提前跳过会让管道喂进来的答案被无视（本轮已踩过并修正）
- **完成判据**：
  - 默认只问关键几项（不刷屏）；可配成"问全部"或"什么都不问"
  - 改过的值**真的生效**（跑完报告里体现）
  - 非交互开关存在且行为正确
  - 参数**来源**能看出来（哪个是默认、哪个是配置来的、哪个是命令行来的）

## T8 · 接入主流程（**必须有**）

- **做什么**：把事件底座、进度、报告、问法接进 `scripts/roughcut.py` 的唯一入口；
  新增开关全部进 `--help` 且**有默认值**
- **影响文件**：`scripts/roughcut.py`
- **依赖**：T1–T7
- **参考资料**：现有 CLI 结构（两段解析 + `SUPPRESS`，帮助里显示真实默认值）
- **完成判据**：`--help` 能看到全部新开关及其默认值；老用法（`--yes`/`--dry-run`）行为不变

## T9 · 端到端验证（**必须有**）

- **做什么**：扩充 `scripts/e2e_roughcut.py`，逐条对 `docs/checklist_observability.md`
- **影响文件**：`scripts/e2e_roughcut.py`
- **依赖**：T8
- **参考资料**：既有 e2e 风格与它踩过的坑（跨轮次脆弱 → **现拍快照**）
- **完成判据**：
  - 正常档跑一次 → 事件文件存在、每阶段有开始/结束、报告路径存在
  - 安静档跑一次 → 终端**没有阶段行**（证明分级真的生效）
  - 把事件文件目录设成不可写 → **业务仍然跑完**（证明观测不影响业务）
  - **变异测试至少 1 次**：故意让某个阶段不发结束事件 → 确认 e2e 变红 → 还原
