## 一、这件事能做的前提（三个坑，全是踩出来的）

| 坑 | 现象 | 真相 |
|---|---|---|
| 模型名 | `cline-pass/...` 我以为不可用 ✗ | **可用** ✓ —— Pass 订阅，不扣余额；402 是 `deepseek/...` 付费路 |
| 响应格式 | 带图请求返回 `empty response content` | 必须发 **`X-Response-Format: openai`**（[官方文档](https://docs.cline.bot/getting-started/clinepass#using-clinepass-outside-of-cline)）|
| token 预算 | 同一帧 `max_tokens=300` 全空、1000 正常 | 这是**推理型**模型，思考 token 会吃光预算 |

三条都修进了代码：
- `observability.openai_client()`（两条客户端）→ `default_headers={"X-Response-Format": "openai"}`
- `vision.py` → 同一个头 + `max_tokens=1000` + **空正文自动 3000 重试一次**

## 三、抽帧的行为

- 先按**场景变化**取；不足再**等距补足**（静态画面也有帧 ✓）
- 帧压到 640 宽 JPEG（42~45KB）
- **踩过的 bug**：等距补足编号从 `len(frames)` 起算，撞上场景帧已用的编号 → **覆盖**一张 ✓。
  已改为接在**已有最大编号之后** ✓，并被 `tests/test_frames.py` 钉住 ✓。

## 四、测试

- `tests/test_frames.py`：4 条（文件名唯一 / 静态画面等距补足 / 视频不存在 / 坏文件读时长）
- 全量：Python **1056 passed / 3 skipped**（1052 + 4）

## 五、未做

## 六、性能：并行与帧数的实测对比（2026-11-08，65s 视频）

| 方案 | 耗时 | 成功率 |
|---|---|---|
| 6 帧 / **串行**（原实现 ✗）| **167.3s** | 5/6 |
| 3 帧 / 串行 | 31.8s | 3/3 |
| **6 帧 / 并行** | **17.1s** | 5/6 |
| 3 帧 / 并行 | 4.8s | 3/3 |

结论：**并行是 10 倍**，减帧只省一半 → **保 6 帧 + 并行** ✓（覆盖更全，17s 可接受）。

### 仍存在的局限

个别帧的视觉调用会返回 `empty response content`（即使重试到 3000 token）✗ ——
网关抖动 / 该帧思考过长。表现是**该帧描述为空 + error 文案** ✓，帧与其余描述照常 ✓。
实测成功率 **5/6 ~ 6/6**，不稳定 ✗。
