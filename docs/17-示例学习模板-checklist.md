## 实机验证记录：`scripts/e2e_fr63.py`（2026-10-19）

```
第一次：30/33 通过   失败项：C2 opening 取自示例首段 / D4' 模板生效 / M5 不传模板仍可生成
第二次：34/34 通过    （改断言后，另加一条更强的 D4''）
```

### 三条失败**全是测试自己的问题** ✗ —— 不是产品缺陷 ✓

**C2 + D4' 同一个根因** ✓：checklist 里 C2 写的是

> `- [x] C2 **mock 模式** opening 取自示例首段（截断 ≤60 字）`

**mock 模式** ✓ —— 规则路径确实是原文摘取（`learn.py:76`：`opening = _clip(paras[0], 60)` ✓）。
但这次跑的是**真实 LLM** ✗，模型给的是**概括**：

```
示例首段 ： 我以前也踩过这个坑，做了半年没什么起色。
模型 opening： 以自身踩坑经历切入，制造共鸣        ← 概括，不是摘取
```

把 mock 模式的行为当硬断言套在真实模式上，**必然会红** ✗。D4' 同理 ——
它拿 `opening[:10]` 去正文里找子串，概括语当然找不到 ✗。

**M5 是另一个飘法** ✓：`status == "qa_passed"` —— 同一份代码、同一段素材，
QA 可能判 `qa_passed` 也可能判 `needs_review` ✓✗。把**模型的主观判定**当硬断言，
必然会飘 ✗。（跟 FR-51 的 G3 是**同一条错** ✓。）

### 改法：断言按**运行模式**分流 + 把"模板生效"换成真检查 ✓✓

| 断言 | 旧（会飘 ✗） | 新（站得住 ✓） |
|---|---|---|
| C2 | 无条件要求原文摘取 | mock → 摘取；真实 → 非空且 ≤60 字 |
| D4' | `opening[:10] in body` | **带模板 vs 不带模板，产出应当不同** ✓ |
| M5 | `status == "qa_passed"` | `status ∈ {qa_passed, needs_review}` ✓ |

**D4'' 是这次真正的收获** ✓✓：原来"模板生效"靠**子串**验（只在 mock 成立 ✗），
现在靠**对照**验 —— 同一素材、同一平台，带模板与不带模板的产出**应当不同** ✓：

```
PASS D4'' 模板确实生效（带模板 vs 不带模板，产出不同） | 带模板 192 字 / 不带 205 字
```

这才是"模板生效"的**真含义** ✓，而且**两种模式下都成立** ✓✓。
