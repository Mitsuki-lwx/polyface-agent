- 关联：docs/05 SRS、06 可行性

## ADR-001 独立自研，不使用 Minds 平台
- 状态：Accepted（2026-09-09）
- 背景：灵感源于 Creative Minds Jam（基于 Minds by Animoca 的持久化智能体），但不想被第三方平台约束。
- 决策：完全独立自研；吸收其"Memory/Continuity/Autonomy"三概念为产品自有能力（本地记忆+断点续跑+复盘）。
- 后果：平台绑定风险消除；记忆能力需自行实现（M4）。

## ADR-002 产品形态：本地一键启动 Web 应用
- 状态：Accepted（**部分被 ADR-019 修订**，2026-10-05）
- 背景：目标用户是个人自媒体博主；"下载即用 + 数据不出本机"曾是信任卖点 —— ⚠️ **该表述不准确，见 ADR-017 修正**。
- 决策：Java(:8080)+Python(:8000) 本地起双服务，浏览器访问；不设云端账号。
- 后果：无服务器成本；分发走 GitHub Releases；单机单用户，简化权限模型。
- 备注（2026-10-05，ADR-019）：本 ADR 当初隐含的「**无需 Node / 无需数据库**」承诺**已撤销**。
  形态改为「**桌面壳 + 后台编辑器 + agent 编排**」，会引入 Node 运行时依赖；
  "本地单机、无云端账号、浏览器/桌面访问"这三点**仍然成立**。

## ADR-003 进程分工：Java 业务编排 / Python LLM 计算
- 状态：Accepted
- 背景：团队熟悉 Java；LLM 管线 Python 生态更顺；单语言会互拖。
- 决策：Java 负责 REST/任务状态机/本地存储/静态托管；Python 只暴露 LLM 计算端点（analyze/brief/draft/qa/generate）。
- 后果：职责清晰可独立测试；进程间通信成本低（本机回环）。

## ADR-004 Java→Python 通信必须强制 HTTP/1.1
- 状态：Accepted
- 背景：JDK HttpClient 默认尝试 HTTP/2 明文升级(h2c)，uvicorn/h11 不支持 → 连接被重置（`header parser received no bytes`）。
- 决策：`JdkClientHttpRequestFactory` + `HttpClient.Version.HTTP_1_1`；封装于 `PythonClient`。
- 后果：调用稳定；后续若换 gRPC/本地管道需另立 ADR。

## ADR-005 本地存储用 SQLite（非 Postgres/pgvector）
- 状态：Accepted
- 背景：单机单用户、零运维优先；无多用户并发与海量向量检索需求。
- 决策：sqlite-jdbc + 自建 schema（material/draft 两表）；数据目录 `data/`（gitignore）。
- 后果：轻量可移植；若未来要相似素材语义检索（M4+）再引入 pgvector/向量方案（另立 ADR）。
- 经验：sqlite-jdbc 多语句 `execute` 只执行首条 → 逐条执行。

## ADR-006 LLM 接入走 OpenAI 兼容适配层 + mock 回退
- 状态：Accepted
- 背景：开源项目不能内置 Key；不同用户用不同模型。
- 决策：`python-service/.env` 配置 base_url/key/model，未配 Key 自动 mock；.env 不入 git。
- 后果：开箱即用（mock）；真实模式模型可随时切换。

## ADR-007 平台 DNA 用 YAML 文件化，随包升级、可用户扩展
- 状态：Accepted
- 背景：平台规则差异大且会变；写死在代码里难维护且更新要发版。
- 决策：`platform-dna/*.yaml` 描述风格/结构/标题/标签/字数/红线/爆款逻辑；代码按 schema 读取。
- 后果：新增平台=新增 YAML；规则更新走小版本包；DNA 全部自研整理规避侵权。

## ADR-008 生成管线四段式（understand→brief→draft→qa）纯代码编排
- 状态：Accepted
- 背景：可控性、可测试性、可解释性优先；暂不需要 LangGraph 级 DAG 编排。
- 决策：Python 模块内顺序编排，平台间 ThreadPool 并行；qa 未过→带反馈重写一轮。
- 后果：逻辑清晰易测；复杂 agent 场景（M4 复盘自主行动）再评估是否引入框架。

## ADR-009 防幻觉：事实清单作为硬约束
- 状态：Accepted
- 背景：自媒体最怕假数据；LLM 会无中生有。
- 决策：understand 抽事实清单 → brief/draft 提示词限定只能使用事实清单 → qa 校验正文数字是否有依据（无依据→warning/拦截）。
- 后果：稿件可信可直发；代价是改写自由度略降（可接受）。

## ADR-010 合规红线：不自动发布 / 不爬平台 / 只处理自有素材
- 状态：Accepted
- 背景：自动发布与批量搬运触碰平台条款与封号风险；热点爬取有数据合规风险。
- 决策：产品只产出"建议稿"，发布动作留在平台由用户完成；热点由用户手动输入；开源叙事强调合规定位。
- 后果：差异化信任背书；部分效率场景（自动发布）明确不做。

## ADR-011 v1 平台范围：先国内 5，海外后置
- 状态：Accepted
- 背景：国内博主是第一用户群；海外平台内容规范差异大。
- 决策：v1 小红书(✅)/抖音/公众号/知乎/B站；X/IG/FB/YT 通过同一 DNA 机制后期加入。
- 后果：DNA 维护节奏可控；海外扩展零架构改动。

## ADR-012 开源与许可证（待最终确认）
- 状态：Proposed（默认 MIT）
- 背景：以开源作为分发与信任渠道。
- 决策：MIT License + GitHub Releases 分发；README 免责声明；CI（测试/打包）M5 落地。
- 后果：代码可被自由使用；品牌/Pro 增值路径（远期）需另行设计。

## ADR-013 AI 剪辑能力分期引入（A 剪辑单 → C 视频入料 → B 自动成片）
- 状态：Accepted（2026-09-09 用户决策）
- 背景：目标平台（抖音/B站/远期 YT）本质是视频平台，只输出文字稿会断掉价值链条；但视频处理（ffmpeg/字幕/TTS）工程复杂度高，不宜与文本引擎同批上线。
- 决策：分三期 ——
  - **A（M3）**：成稿附"剪辑单"（分镜时间轴/画面建议/字幕断句/BGM·转场提示），纯 LLM，随 Web 工作台交付；
  - **C（M3.5）**：视频/音频 → 转录口播稿 → 复用 understand 管线，解决"用已有视频做素材"入口；
  - **B（M5+ 专项，含 B1+B2）**：
    - B1 图文成片：无视频素材时，图片+TTS+字幕 → 短视频 MP4；
    - B2 智能剪已有视频：原始录像 → 自动去停顿/自动字幕/分镜/可选卡点 → 初剪成片。
    技术方向：ffmpeg + silencedetect/auto-editor（去停顿）+ Whisper/WhisperX（本地字幕）+ ffprobe scene（分镜）。
- 后果：价值链条闭合；仅本地产出、不自动上传（延续 ADR-010 红线）；B 需要引入 ffmpeg/TTS/转写依赖，单独立项评估。
  现实边界：行业普遍为"AI 预剪 + 模板参数 + 人工审片"，不做零人工全自动承诺（防止过度承诺）。
- 备注：用户 2026-09-09 确认 B1+B2 都要，B 维持 M5 专项（不提前到 M4）。
  ⚠️ **「专项」措辞已弃用（见 ADR-018）**：2026-09-16 用户确认成片定位为
  「核心方向 · 当前后置」——排序不变（仍不提前），但不再称"专项"（易被误读为附加功能）。

## ADR-014 用户模板 = 用户级覆盖层（内容模板/成片模板/示例学习）
- 状态：Accepted（2026-09-09 用户决策）
- 背景：仅"平台 DNA"产出是"平台的味道"而非"博主的味道"；博主常有固定套路。竞品=平台给模板，本产品应让用户模板成为资产。
- 决策：
  - 模板分两类：**内容模板**（开头/结构/结尾/口播框架，M3 基础版）、**成片模板**（片头/转场/字幕/节奏/BGM 偏好，M5 B 阶段用）；
  - 优先级：用户模板 > 平台 DNA（结构/风格部分）；**平台 limits/红线 恒强制执行**，不可被模板覆盖；
  - 模板存用户数据目录，支持导出/备份/开源共享；随稿记录模板版本号（可追溯）；
  - 示例自动学习（喂 1 篇爆款/示例片拆解出草稿模板）推迟 M4+，且**产物须人工确认后才启用**。
- 后果：差异化增强（个性化 + 可追溯）；模板层接入现有 brief/draft 提示词（把模板并入素材侧上下文）；需要模板 CRUD 存储。

## ADR-015 前端采用无构建静态 SPA（本地工具优先，非 React）
- 状态：Accepted（2026-09-09，M3 落地）
- 背景：蓝图曾规划 React+Vite；但对"本地一键启动、单机单用户"的工具而言，引入 Node 构建链会抬升启动与分发复杂度。
- 决策：Web 工作台 v1 = 单文件静态 SPA（`java-backend/src/main/resources/static/index.html`），由 Java 直接托管；无 npm/构建依赖。
- 后果：启动即用、分发即 jar+static；交互复杂度上去后（复盘看板/模板库管理）可再迁 React（届时新 ADR）。
- 备注：React 仍保留为"演进选项"，不构成架构承诺。

## ADR-016 可观测性：本地优先 + Langfuse 可选接入（FR-70~72）
- 状态：Accepted（2026-09-12，M5c 落地）
- 背景：真实链路首次跑通时暴露出三个问题——① 上游额度极紧（连续两次调用即 429），失败原因不可见；② 无法回答"这次生成慢在哪、用了哪个模型、重试几次"；③ `openai` 依赖从未安装却因 mock 优先而长期未被发现（说明"能跑通"缺乏真实验证）。
- 决策：
  1. **本地用量必选**：每次 LLM 调用写本地 JSONL（`{data-dir}/llm-usage.jsonl`），只记模型/耗时/token/重试/错误类型，**不记 prompt 正文**（避免本地文件成为泄漏源）；Java 侧只做转发，维持"Python 不碰数据库"的既有边界。
  2. **Langfuse 可选**：默认关闭；启用时 Python 用官方 v4 SDK（drop-in `langfuse.openai`，自动捕获 model/token），Java 手写 Public Ingestion API（纯 JDK HttpClient，**零新依赖**）。上报 **fire-and-forget**，失败仅告警。
  3. **可达性探测 + 静默降级**：Langfuse 不可达时整体关闭观测，**业务零影响**（实测验证）。
  4. **trace_id 用 W3C 32 位 hex**：由 Java `TraceFilter` 生成并写入响应头，经 `X-Trace-Id` 传给 Python；线程池须用 `run_in_context` 显式传播（`ThreadPoolExecutor` 不继承 `contextvars`）。
- 后果：
  - 无 Langfuse 也能查用量与错误分布；接入 Langfuse 后可得完整 trace 树（root `generate:xhs` → understand/brief/draft/qa → generation）。
  - **不引入任何硬依赖**，不违背 ADR-002「本地一键启动」。
  - 观测数据默认不出本机；若启用 Langfuse 且指向云端，则由用户自行承担（默认 host 为 localhost）。
- 备注：prompt/response 正文**只在用户自建的 Langfuse 实例**中出现；本地与日志一律脱敏。

## ADR-017 数据边界：修正"数据不出本机"的不实表述

- 状态：Accepted（2026-09-16）
- 背景：09-14 独立评估指出「"下载即用"和"数据不出本机"都需要收回到真实边界」。复核确认：
  - **生成链路全部调用外部 LLM**：`understand.py`（素材解析，送出 `raw_text` **全文**）、`generate.py`（每平台 brief/成稿/剪辑单/QA **最多 4 次调用**，QA 不过还会带反馈重写一轮）、`learn.py`（示例学习）
  - 默认端点为 `https://token.sensenova.cn/v1`（`config.py`）—— **第三方云服务**
  - 因此"数据不出本机"**不成立**：素材正文会离开本机
- 决策：
  1. **区分"存储"与"传输"**：素材/稿件/模板/画像**只存**本机 SQLite（这条成立）；但**生成过程会把素材正文发送给用户自行配置的 LLM 服务商**
  2. **对外表述统一改为**："素材与稿件存在你的电脑；生成时会把素材正文发送给你自己配置的 LLM 服务商。音视频转写全程本地，不上传。"
  3. **音视频转写的"无外部上传"继续成立**（本地 ASR / 字幕提取，见 ADR-010、UC-12）—— 不因本决策放宽
  4. 同步修正 NFR-01（"无外部服务依赖"→"进程间无外部中间件依赖"）与 NFR-04（"≤60s"→实测 60~250s）
- 后果：
  - 信任卖点从"数据不出本机"改为"**数据只存在你本机 + 模型用你自己的 Key**"——卖点仍在（不经平台方、无云端账号），但不再暗示"完全离线"
  - 需在 README 增补**数据边界**章节，让用户在使用前就知道哪些内容会出网
  - **仍待办**：`start.bat` 依赖开发机路径 + venv/Maven，"下载即用"同样不成立 —— 属「最小启动包」任务（第二关）
- 备注：`mock` 模式（`LLM_MOCK=true`，无 Key 时默认）**全流程离线**，此时"数据不出本机"成立；但产出是演示结果，非真实生成。

## ADR-018 自动成片定位确认：**核心方向 · 当前后置**；首发 B1 图文成片
- 状态：Accepted（2026-09-16 用户决策）
- 背景：ADR-013（2026-09-09 用户决策）把 B 定为「**M5+ 专项**（不提前到 M4）」。但用户 2026-09-14 表述
  「**AI 剪辑是核心路径之一，而不只是文案改写的附加功能**」——「专项」一词极易被读成"附加功能"，
  与"核心路径"的定位不符；且该表述当时**未落档**（起草文档的会话因额度耗尽中断）。
  核对后确认：二者并非真冲突——**09-09 说的是"排序"（不提前到 M4），09-14 说的是"定位"（是核心而非附加）**。
- 决策：
  - **定位**：自动成片是**核心方向**（不是文案改写的附加功能）；
  - **排序**：**当前后置** —— 先完成第三关（真实作者验证，见 `docs/50`）再投入工程。
    「专项」这一措辞**不再使用**（易误读）；
  - **首发形态**：**B1 图文成片**优先；B2 智能剪已有视频排在其后；
  - **成片优化目标平台**：小红书、抖音、B站；
  - **TTS 选型：暂不决定**，实施前必须评估（取舍见下）。
- 后果：
  - 文档措辞统一：`docs/05` FR-52/53、`docs/06` 路线图与可行性表、`README` 路线图同步改为
    "核心方向 · 当前后置"；
  - ⚠️ **B1 设计必须避开抖音官方的低质判定**：抖音明文将「单图 + 大量文字」「模板感强的图片轮播」
    列为低质内容（见 `docs/33` DNA 调研 v2）。**最省事的图文成片形态恰好是被打击的那一种**，
    必须在设计阶段就吸收，不能做完再发现；
  - 仍坚持"**AI 预剪 + 人工定稿**"，不做零人工全自动承诺（延续 ADR-013 现实边界）；
  - **TTS 未决是一个必须先回答的前置问题**：云端 TTS 会把**成稿全文**再发给一家服务商 →
    需扩写 ADR-017 与 README 的数据边界表；本地 TTS 则给发布包再加数百 MB 级依赖，
    与 M5 刚做成的"解压双击即用"存在**直接张力**（可复用 `asr.py` 的"可选依赖 + 降级"策略）。
- 备注：定位是"核心"、排序是"后置"，两者不矛盾。**本 ADR 只改定位与措辞，不改变"尚未实现"这一事实**。
  溯源与待决项清单见 `docs/49-产品定位与自动成片主张.md`。

## ADR-019 交付形态改向：放弃「无需 Node / 无需数据库」，改为**桌面壳 + 后台编辑器 + agent 编排**

- 状态：Accepted（2026-10-05 用户决策）
- 背景：用户 2026-10-05 明确：「**无需 node 和无需数据库这条不要了，先做出来再想能不能做的小一点**」，
  目标形态是「**轻量化单机桌面端应用**，那两个开源应用运行在后台，由 agent 做」。
  即：polyface 不再把自己限制成"零外部运行时的浏览器工具"，而是**编排者** ——
  由它驱动成熟的开源编辑器在后台完成**做图**与**剪辑**，自己专注"素材 → 多平台稿件 → 成片"的编排与 LLM 环节。
- 调研（一手证据，2026-10-05 实测/API 核对）：

  | 候选 | 事实 | 能否被 agent 后台驱动 |
  |---|---|---|
  | **gimpish**（`jvanderberg/gimpish`，MIT，npm 0.1.0） | 自述 "Agent-native image composition"：`scene.json`（zod 版本化契约）+ 语义 CLI 动词 + `serve` HTTP + **MCP 端点 `127.0.0.1:8767/mcp`**（`get_scene`/`set_scene`/`edit_text`/`remove_background`/`export_png`/`undo`…）。依赖 Node ≥20.19 + sharp + onnxruntime-node（U²-Net 背景去除模型 176MB 首次下载） | ✅ **实测可后台驱动**：本机装 `gimpish@0.1.0` 后，写 `scene.json` → `gimpish -C <dir> export --out x.png`，**474ms** 产出 1080×1440 PNG（中文字体正常） |
  | **OpenCut**（`OpenCut-app/OpenCut`，MIT，92.5k★） | rewrite 的桌面端自述原文：「**Very early. Right now this is just a window that opens.**」；README 把 *Editor API / 插件 / MCP server / headless mode* 全部列为 **coming**；classic 版（`opencut-classic`）**已归档不再维护**，且其 contributing 明确 "**Avoid for now: … export functionality**"（导出正在被二进制渲染方案重写） | ❌ **当前不可驱动**：没有 headless 入口、没有 API、没有 MCP；桌面端是空窗口 |

- 决策：
  1. **撤销**「无需 Node / 无需数据库」这条交付承诺（README / ADR-002 / `docs/48` 相关表述须同步改写）。
     这条承诺当初是 M5「解压双击即用」的依据；现在以**能力**优先于**体积**，瘦身留到"做出来之后"。
  2. **架构改为「桌面壳 + 后台编辑器进程 + agent 编排」**：polyface 定义**编辑器适配器**接口，
     首个适配器 = **gimpish（做图/封面/图文卡片）**；视频剪辑适配器**先用 ffmpeg**（已是既有依赖），
     **OpenCut 适配器预留但不实现**（等其 headless / Editor API 落地；届时只需新增一个适配器，不动编排层）。
  3. **不 fork、不内嵌源码**：一律以**独立进程 + 官方接口**（CLI/HTTP/MCP）驱动，MIT 许可下仅借鉴设计。
     理由：OpenCut 处于重写期、gimpish 处于 0.1.x，内嵌源码等于把它们的重构成本转嫁给自己。
  4. **降级策略沿用既有约定**：编辑器缺失 → `needs_manual` + 安装指引，**不抛 5xx**（同 `asr.py` / `ingest.py`）。
  5. **排序变更**：ADR-018 的"第三关（真实作者验证）先行"**被本决策暂停**（用户明确"先做出来"）。
     第三关**不取消**，改为与 M6 并行推进。
- 后果：
  - 发布包体积会显著增大（需带 Node 运行时 / 编辑器依赖），与 M5 的交付叙事冲突 —— 这是**用户明确接受的取舍**；
  - 新增"编辑器进程管理"职责（启动/端口/健康检查/退出清理），归入桌面壳任务（M6-2）；
  - 首个落地切片（M6-1）刻意**不依赖桌面壳**：先用 Python 适配器 + 现有 Web UI 验证
    "agent 驱动后台编辑器出图"这条链路，壳留到链路验证之后再做；
  - **TTS（ADR-018 的 Q3）仍然未决**，本决策不改变它。
- 备注：本 ADR **只改交付形态与排序**，不改变 FR-52/53「尚未实现」这一事实；
  成片的**定位**仍是「核心方向」（ADR-018 未变）。
