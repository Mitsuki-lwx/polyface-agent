# spec —— TTS 插件系统

版本：2026-10-11　　对应 tasks：`docs/tasks_tts_plugin.md`　　验收：`docs/checklist_tts_plugin.md`
上游：`docs/spec_b1.md`（图文成片）· ADR-017（数据边界）

---

## 1. 背景

B1 做完时，配音只有**一个**内置后端（Windows SAPI），而本机的中文音色**只有一个女声** ——
"提供几种不同的配音"这件事从根上做不到。

试过两条内置的路，都撞墙：

| 方案 | 撞在哪 |
|---|---|
| **Kokoro**（Apache-2.0、音色多） | 要求 Python `<3.13`（本项目 3.13）· 中文 G2P 拉 **jieba**（本机稳定 segfault）· 模型在 HuggingFace（本机连不上） |
| **piper** | GPL-3.0 · 音色模型同样在 HuggingFace |

**这些全是"内置后端"的麻烦。** 换个思路：用户手里有什么（自己的模型、自己的 API、
自己录的配音），让他自己接进来 —— 那就没有任何一个方案能卡住整个产品。

## 2. 目标用户

**现阶段只有作者本人**：他可能想用 Kokoro、想接某个云端 TTS、想直接用自己的录音。
他不该为了换一个音色去改这个项目的源码。

## 3. 能力清单（一句话一条）

1. **插件就是一个目录**：里面放 `plugin.json`（声明能力/音色/入口）+ 一个可执行入口。
   拷进去就生效，不用装 Python 包、不用改代码
2. **入口可以是任何语言**：约定是"读 stdin 的 JSON、写 stdout 的 JSON"，所以 Python/Node/Go/一个 shell 脚本都行
3. **统一清单**：程序把**所有**可用方案（内置的 + 插件的 + "用户自己的配音"）列成**一张清单**，
   用户挑哪个用哪个 —— **不是二选一，是把选择摆出来**
4. **选到分镜级**：每个分镜可以指定不同来源（旁白用一个、对话用另一个）
5. **插件坏了不能拖垮主流程**：某个插件报错 → 只影响用到它的那一步，其余照跑
6. **如实告知**：装插件等于**执行别人的代码** —— 界面上要明说；记录里写清这次用了哪个插件
7. **内置的几个也走同一套接口**：SAPI / 用户自己的音频 / （以后）Kokoro ——
   内置与插件用**同一个**调用路径，否则插件的接口永远没被真正用过

## 4. 非功能要求

- **数据边界不变**：插件机制本身不引入任何外部服务。**插件自己接云端 API 是用户的选择**，
  但那必须由插件声明（`"network": true`），程序如实转述给用户
- **不沙箱**（用户拍板）：本地工具、自己装的插件，就是能跑任意代码。
  换来的是"支持任意语言、任意模型"。**代价写在界面上，不藏**
- **清单要可发现**：`GET /api/tts/plugins` 能列出插件、音色、参数、以及**它是否要联网**
- **失败要说清是哪个插件**：不能只说"配音失败"
- **不破坏已有能力**：SAPI 与"自己的配音"现在就能用，迁移过程里不能坏

## 5. 设计骨架

```
python-service/tts-plugins/
  windows-sapi/                 ← 内置：系统语音
    plugin.json
    run.py
  own-audio/                    ← 内置：用户自己的音频（逐分镜给文件）
    plugin.json
    run.py
  kokoro-zh/                    ← 示例：用户自己放的（模型在别处，见 fetch_kokoro.py）
    plugin.json
    run.py
  <用户自己拷进来的任意目录>/
    plugin.json                 ← {id, name, kind:"tts", languages, voices, run, network}
    <任意语言的入口>
```

**调用约定（唯一的接口）**：

```
程序 → 插件（stdin 一行 JSON）:  {"text": "...", "voice": "...", "out": "/abs/out.wav",
                                 "rate": 0, "volume": 100, "params": {...}}
插件 → 程序（stdout 一行 JSON）: {"ok": true, "seconds": 1.23}  或  {"ok": false, "error": "..."}
```

插件负责把音频写到 `out`（**WAV**）。其余不管。

**关键决定一：契约只有一个 —— stdin/stdout 的 JSON。**

不定义 Python 基类、不定义 import 路径。这样 Node/Go/shell 都能写插件，
而且"内置后端"与"第三方插件"走的是**同一条路** —— 内置的那几个因此成了接口的第一批真实用户，
接口定错会立刻暴露。

**关键决定二：`plugin.json` 里必须声明 `network`。**

插件可以联网（比如接云端 TTS），但那**改变了数据边界**（ADR-017）。
程序不阻止，但必须**如实转述**：清单里标出来、UI 上提示、记录里写上。
"我没偷偷把你的稿子发出去"这句话得能验证。

**关键决定三：不做沙箱，但把代价说清楚。**

沙箱会直接干掉"任意语言、任意模型"这个好处（也是用户要它的原因）。
所以选择是：**不沙箱 + 明确告知**。装插件时的提示、清单里的标记、
以及"这个插件能执行任意代码"这句话，都是这个决定的兑现方式 —— 不是免责声明，是如实说明。

**关键决定四：清单是**一张**，不是几个后端各自为政。**

`tts.catalog()` 返回**所有**来源的统一清单：内置的、插件的、以及"用户自己的配音"。
用户看到的是一个列表，不是一个"选后端"的下拉框。
这样"提供多种方案给用户选"才是字面意义上的成立。

**其它骨架决定：**

- 插件的调用走**子进程**：天然隔离崩溃（插件 segfault 不会带走主进程 —— 这一点对本机
  的 jieba 问题尤其重要）
- 音色可以由插件声明（`voices: [...]`），也可以只声明语言
- 插件目录可配（`POLYFACE_TTS_PLUGINS`），默认 `python-service/tts-plugins/`
- 记录里写清每个分镜实际用了哪个插件/音色

## 6. Out of Scope（本版不做）

- **别的部分插件化**（LLM / 渲染 / 封面）—— 用户明确说"先只做 TTS"；
  先把一个点做透，通用接口在没跑过几个真实插件之前定不对
- **插件市场 / 在线安装** —— 拷目录就够
- **插件签名 / 校验** —— 本地工具，自己装的自己负责（见关键决定三）
- **沙箱**（见关键决定三）
- **插件的参数 UI 自动生成** —— 先列出来让人填，不做动态表单
