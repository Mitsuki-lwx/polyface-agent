# tasks —— 任务断点续跑（生成 + 粗剪）

上游规格：`docs/spec_resume.md`　　验收：`docs/checklist_resume.md`

> 10 个任务，每个能在一次专注会话内完成。
> **最后两个（T9 接入主流程 / T10 端到端验证）是硬要求，不许跳过。**
> **T10 必须真的中断一次**（不是"假装中断"）—— 否则测不出续跑。

---

## T1 · 落盘契约（先定契约，再改实现）

**影响文件**：`docs/spec_resume.md`（补一节）· `python-service/app/pipeline/runlog.py`（或新建）

**依赖**：无

**做什么**：定死「已完成单位」的落盘格式与位置。**这个契约是 Python 与 Java 两侧的共同接口**，
先定死，后面两侧才能并行。

要定死的：

| 项 | 约定 |
|---|---|
| 目录 | `<job workdir>/done/` |
| 文件名 | 生成：`platform-<code>.json`；粗剪：`stage-<name>.json` |
| 内容 | 该单位的**产物**（生成的稿子 / 粗剪该阶段的产物路径） |
| 写入方式 | **临时文件 + 改名**（原子）—— 写一半崩掉不能留下坏 JSON |
| 可读性 | 单文件必须是合法 JSON；解析失败一律当"没完成"（**不猜**） |

**验收**：写一个单元测试证明"写一半崩掉不会留下可解析的半成品"。

---

## T2 · Python：生成逐平台落盘

**影响文件**：`python-service/app/pipeline/generate.py`（`_generate_one` 或编排处）

**依赖**：T1

**做什么**：每完成一个平台，**立刻**把该平台的产物写进 `done/platform-<code>.json`。
现在是攒齐所有平台再一起返回，中断即全丢。

**要注意**：`generate()` 是**可部分成功**的（`failures` 列表）—— 失败平台的格子不落盘。

**验收**：跑一次 2 平台的生成，workdir 里出现 2 个 `platform-*.json`，内容与返回的稿子一致。

---

## T3 · Python：粗剪逐阶段落盘

**影响文件**：`python-service/app/pipeline/roughcut.py` · `scripts/roughcut.py`

**依赖**：T1

**做什么**：粗剪**本来就"中间产物落盘保留"**（`docs/spec_roughcut.md` §4）——
剪后视频、字幕文件、剪点 JSON 都在。本任务把它们**登记**成 `done/stage-*.json`，
让续跑能判断"从哪一步接着走"。

**验收**：粗剪跑到"转写"失败时，`done/` 里有 `stage-探测/找停顿/剪/抽音轨`，没有"转写"。

## T4 · Java：`interrupted` 状态 + 改造 `recoverInterrupted`

**影响文件**：`java-backend/.../store/Store.java` · `job/GenerateRunner.java` · `job/RoughcutRunner.java`

**依赖**：T1

**做什么**：

1. `Store` 加 `JOB_INTERRUPTED` 常量（状态值新增，**不改既有值**）
2. `recoverInterrupted()` 从「标为 `failed`」改成「标为 `interrupted`」
3. 保留原注释的关切（"否则工作台会永远转圈"）—— `interrupted` 也是终态之一，
   工作台不会转圈 ✓

**验收**：见 checklist §3 —— 启动时有未结束任务 → 状态是 `interrupted`，**不是** `failed`。

---

## T5 · Java：续跑（只跑缺的）+ 合并产物

**影响文件**：`job/GenerateRunner.java` · `job/RoughcutRunner.java`

**依赖**：T2、T3、T4

**做什么**：

- 读 `done/` 里已完成的单位 → 算出**缺哪些**
- 生成：用**缺的平台**调 `generate()`（接口本来就接受子集）
- 粗剪：从**最后一个完成的阶段之后**接着跑
- 合并产物 → 与"一次跑完"等价

**这是本设计的核心不变量**：落盘粒度 = 续跑粒度。

**验收**：构造一个"3 个平台已完成、2 个缺"的任务 → 续跑后**只调了 2 个平台**
（用 LLM 调用次数或日志证明），最终产物 5 个齐全。

---

## T6 · 端点：`/api/jobs/{id}/resume`

**影响文件**：`java-backend/.../web/JobController.java`

**依赖**：T5

**做什么**：新增一个续跑端点。与既有 `retry` 的区别要**说清楚**：

| | `retry` | `resume` |
|---|---|---|
| 适用状态 | `failed` | `interrupted` |
| 行为 | **从头**再跑 | **跳过已完成的**，只补缺的 |

状态不对时要**明确报错**（拿 `failed` 的任务调 `resume` 应当被拒，反之亦然）——
静默接受会让用户以为"续跑了"其实是"重跑了"。

**验收**：状态不匹配 → 明确 4xx 与可读理由。

---

## T7 · 前端：「已中断 · 可继续」

**影响文件**：`java-backend/src/main/resources/static/index.html`

**依赖**：T6

**做什么**：任务列表里 `interrupted` 的任务显示「已中断 · 可继续」+ 「继续」按钮；
点了调 `resume`。文案要能让人分清"失败"与"中断"。

**验收**：浏览器实测（真中断一个任务 → 看到「可继续」→ 点了真的接着跑）。

---

## T8 · 取消 / 删除 `interrupted` 任务

**影响文件**：`JobController.java` · `Store.java`（如需要）

**依赖**：T4

**做什么**：`interrupted` 的任务也要能取消/删除，不留垃圾。既有的 `cancel` 端点要认这个新状态。

**验收**：`interrupted` 的任务能被取消；取消后不再出现在"可继续"列表里。

---

## T9 · 接入主流程（**必须有**）

**影响文件**：两个 runner · 相关测试

**依赖**：T1~T8

**做什么**：把落盘 → 中断 → 继续接成一条链，并确认**失败与中断没有混用**：
`failed` 的任务不该出现「继续」按钮，`interrupted` 的不该显示成"失败"。

**验收**：走一次真实流程，状态流转清晰可查。

---

## T10 · 端到端验证（**必须有**）

**影响文件**：无（验证任务）

**依赖**：T9

**做什么**：**真的中断一次**。

步骤（不许偷懒成"直接调 resume"）：

1. 起服务，提交一个 5 平台的生成任务
2. **等它跑到一半**（比如已完成 2~3 个平台）→ **真的杀掉服务进程**
3. 重启服务 → 确认任务状态是 `interrupted`（**不是 `failed`**）
4. 点「继续」→ 确认**只跑了缺的平台**（LLM 调用日志为证）
5. 确认最终产物 **5 个平台齐全**，且与"一次跑完"的产物结构一致
6. 粗剪同样来一遍（它的中断点更容易落在"转写"这种慢阶段）

**验收**：上面 6 步的原始输出都留着；**哪一步没做到就如实写没做到**。
