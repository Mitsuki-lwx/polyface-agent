# 任务书：长任务预算与部分失败保留

- 文档类型：task（事前三件套之一）
- 版本：v1.0 · 日期：2026-09-16
- 关联：FR-70（调用加固）、FR-42（成稿）、NFR-01（性能）、ADR-004（HTTP/1.1）
- 前置：事实确认闭环已完成（`docs/42`）；09-14 独立评估第 4 类问题**尚未处理**

---

## 1. 背景（评估报告指出的第 4 类问题）

> 「长任务和发布承诺不匹配」

**已复核确认的缺陷**：

| # | 缺陷 | 证据 |
|---|---|---|
| 1 | Java 调 Python 的读取超时**固定 180 秒** | `PythonClient.java` |
| 2 | 真实单平台生成曾耗时 **250 秒** | `docs/34` §3.2 实测记录 |
| 3 | 因此**即使 Python 最终能生成，前端链路也可能先超时** | 设计预算冲突 |
| 4 | Java **等到全部平台返回才逐稿落库** | 中途失败 → **已完成平台的产物也丢失** |
| 5 | Python 串行阶段异常**直接向上抛出** | 后续平台失败会丢掉前面平台的成果 |

**本质问题**：把"多平台批量生成"当成了一个**原子操作**，但它是**可以部分成功**的。加上上游额度紧张（单平台 100~250s），这个设计在真实条件下很容易让用户白等一场、且什么都拿不到。

## 2. 目标

1. **部分成功必须保留**：某平台失败**不影响**其他平台已完成的稿子，且失败可单独重试
2. **超时显式化**：超时是**可配置的预算**（不是魔法数字），并在文档/UI 里说清
3. **用户可预期**：前端明确显示「X 成功 / Y 失败」+ 失败原因，而不是一个笼统的 502
4. **默认更稳妥**：默认单平台（评估建议），降低一次性长任务的风险
5. **不引入重型基础设施**：**不做**后台任务队列/分布式调度（评估明确说"不需要立刻上"）

## 3. 范围

### In

| # | 事项 |
|---|---|
| 1 | **Python 逐平台容错**：单个平台失败 → 记录到 `failures`，其余照常返回 |
| 2 | 生成响应新增 `failures: [{platform, error}]` |
| 3 | **Java 部分落库**：成功的照常落库；失败的记入响应（不整体 502） |
| 4 | `PythonClient` 超时改为**可配置**（`polyface.llm.timeout-sec`），并在日志中打印实际预算 |
| 5 | **前端**：显示成功/失败数 + 失败平台与原因 + **「重试失败平台」**按钮 |
| 6 | 前端默认只勾选**单平台**（可多选，但给出耗时提示） |
| 7 | 文档：明确"单平台预计耗时"与超时预算的关系；`docs/29/34` 的预估做勘误 |
| 8 | 测试：Python 部分失败、Java 部分落库、前端失败提示（浏览器实测） |

### Out

| 事项 | 原因 |
|---|---|
| 后台任务队列 / 异步任务 + 轮询 | 评估明确：**不需要立刻上**；先做部分成功保留，成本低收益大 |
| 分布式任务平台 / 消息队列 | 同上，且违背"本地一键启动"（ADR-002） |
| 断点续传 / 跨会话恢复任务 | 属下一阶段（若部分成功仍不够） |
| 单平台自动重试 N 次（应用层） | 已有 llm.py 内的重试+降级；本次不加额外层（避免放大额度消耗） |
| 隐私表述 / CORS / 启动包 | 属第一关其余项与第二关，独立任务 |

## 5. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 部分成功后用户以为全成功 | 误用 | UI 明确列出失败平台与原因，不用"完成"一概而论 |
| 超时调大导致用户等更久 | 体验 | 不默认无限延长；给出**单平台预计耗时**提示；默认单平台 |
| 逐平台容错掩盖系统性问题 | 难排查 | 失败全部记入 `failures` + 日志；**不静默** |
| 改动生成主流程 | 回归 | 既有测试必须全绿；容错只包在单平台调用外层 |

## 6. 完成定义（DoD）

- [ ] 三件套齐备
- [ ] Python 单平台失败时，其余平台仍返回结果（有测试）
- [ ] 响应含 `failures`（平台 + 原因）
- [ ] Java 部分落库：成功平台入库，失败平台不阻塞（有测试）
- [ ] Java 超时可配置，且启动/调用时日志可见
- [ ] 前端显示成功/失败数 + 原因，可**重试失败平台**
- [ ] 前端默认单平台（多选时提示预计耗时）
- [ ] 既有测试全绿（Java 39 / Python 64）+ 新增测试全绿
- [ ] 端到端：部分失败场景验证通过 + 浏览器实测
- [ ] 文档勘误 + 交付说明 + 提交

## 7. 待确认项

| # | 问题 | 建议默认 |
|---|---|---|
| Q1 | 超时默认值？ | **240s**（单平台实测上限 ~250s 留余量；可配）；**不设无限** |
| Q2 | 全部平台都失败时？ | 仍返回 200 + `failures` 全列（让前端展示原因），**不 502** |

| Q5 | Java 侧整体超时如何处理？ | 捕获超时 → 返回**已落库的部分** + 明确提示"其余平台超时未完成" |
