# 任务书：LLM 运行时加固 + 全链路可观测

- 文档类型：task（事前三件套之一）
- 版本：v1.0 · 日期：2026-09-11
- 关联：`05-SRS` NFR-04（响应时间）/ NFR-08（可测试）；新增 **NFR-10（可观测性）**；`08-ADR` 新增 ADR-015（观测数据本地优先 + 可选 Langfuse）
- 前置：M5 Release 打包（`docs/23/24/25`）**暂缓**，理由见下

---

## 1. 背景（基于本轮实测，非推测）

用户在推进 M5 Release 前提出质疑：「这么快到打包了吗」「各平台怎么转真的做到了吗」「全链路观测呢，可以用 langfuse」。实测后发现**三个硬问题**：

| # | 问题 | 证据 |
|---|---|---|
| 1 | **真实 LLM 链路从未跑通** | `requirements.txt` 写了 `openai>=1.40`，但环境**从未安装**；`llm.py` 用函数内延迟导入，mock 模式永远走不到 → 缺失被完全掩盖 |
| 2 | **无任何可观测性** | `grep langfuse\|trace_id\|opentelemetry` → **0 结果**；只有 INFO 级 logging |
| 3 | **上游额度极紧** | 商汤网关 8 个模型 `pricing=0` 但**连续两次调用即 429**（`tpm/rpm limit`）；部分模型 `insufficient_quota` |

**结论**：在"真实链路能否稳定跑通"未解决前做 Release 打包，等于**把未验证的东西打包发出去**。故调整优先级。

## 2. 目标

1. **真实链路稳定可用**：限流可重试、额度耗尽可降级、失败可解释
2. **全链路可观测**：一次生成的 trace 贯穿 `SPA → Java 编排 → Python 管线 → LLM 调用`，在 Langfuse 可查
3. **失败可诊断**：能回答"这次生成慢在哪、失败为什么、用了哪个模型、重试几次"
4. **不破坏既有约束**：观测**默认可用**（本地落库）、Langfuse **可选启用**；仍满足 NFR-02 数据本地

## 3. 范围

### In（本任务做）

| # | 事项 |
|---|---|
| 1 | `llm.py` 加固：**超时**、**重试 + 指数退避**、**错误分类**（限流/额度/网络/解析） |
| 2 | **模型降级链**：主模型额度耗尽时自动切备用模型（网关多模型配额独立，实测有效） |
| 3 | **trace_id 贯穿**：Java 生成 → HTTP header 传给 Python → 关联所有 LLM 调用 |
| 4 | **本地用量落库**（SQLite `llm_call` 表）：模型/token/耗时/重试次数/成功失败 —— **不依赖 Langfuse 也能查** |
| 5 | **Langfuse 上报**：Python 侧官方 SDK + Java 侧手写 HTTP（移植 `lwx-ai-agent` 的 `LangfuseReporter`） |
| 6 | **真实模式冒烟测试**：pytest marker，配了 Key 就跑真实调用（防止 mock 再次掩盖问题） |
| 7 | 前端：生成结果区显示 trace 摘要（模型/耗时/重试次数） |
| 8 | 交付说明 + 更新 SRS（NFR-10）/ ADR-015 |

### Out（本任务不做）

| 事项 | 原因 |
|---|---|
| Langfuse prompt 版本管理 / 评估数据集 / LLM-as-Judge | 属"效果优化"阶段，需先有稳定数据积累 |
| 成本核算 | 当前模型免费 |
| 分布式追踪（OpenTelemetry 全家桶） | 单机两进程，trace_id 手动传播足够 |
| 日志聚合/告警 | 单用户本地工具，过度设计 |
| 平台 DNA 质量重做 | **独立任务**（本轮已识别为缺口，另开三件套） |

## 5. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **上游额度极紧**（连续两次即 429） | 真实链路跑不完 5 平台 | ①重试+退避 ②模型降级链 ③生成时**串行化** LLM 调用（牺牲并发保成功） |
| 免费额度可能随时耗尽 | 功能不可用 | 明确报错 + 引导换 Key；降级链覆盖多模型 |
| Langfuse SDK 版本迭代快 | 接法过时 | 按 skill 要求**先查官方文档**再写；Java 侧用手写 HTTP 规避 SDK 风险 |
| 上报阻塞业务 | 响应变慢 | fire-and-forget，失败仅告警 |
| 用量表膨胀 | 本地库变大 | 只存摘要（不存完整 prompt/response），可清理 |
| 把 Key 写进日志/上报 | 泄密 | 日志与上报**统一脱敏**（Key 永不落盘、永不外发） |

## 6. 完成定义（DoD）

- [ ] 三件套文档齐备且已确认
- [ ] **真实模式**跑通完整链路：素材 → 5 平台生成（含 QA）
- [ ] 429 能被自动重试并最终成功（有日志与用量记录为证）
- [ ] 额度耗尽时自动降级到备用模型
- [ ] 一次生成在 Langfuse 可见完整 trace（含 outline/understand → 各平台 brief/draft/qa）
- [ ] 本地 `llm_call` 表可查到每次调用的模型/耗时/token/重试次数
- [ ] 真实模式冒烟测试可独立运行（无 Key 时自动 skip）
- [ ] mock 模式全链路仍可用（不因加固而破坏离线能力）
- [ ] 交付说明产出并提交

## 7. 待确认项

| # | 问题 | 建议默认 |
|---|---|---|
| Q1 | 模型降级链顺序？ | `deepseek-v4-flash`（主）→ `kimi-k3`（备）→ `sensenova-u1-fast`（备） |
| Q2 | 限流时是否串行化多平台生成？ | **是**。默认并行（快），检测到 429 后本轮转为串行 + 退避 |
| Q3 | 是否存完整 prompt/response？ | **本地存摘要**（前 500 字）；Langfuse 上报完整（用户自己的实例） |
| Q4 | 前端 trace 展示深度？ | 只显示「模型 / 耗时 / 重试次数」，不暴露完整 prompt（避免误截图泄漏） |
| Q5 | 是否同时把 Java 侧也接入 Langfuse？ | **是**（trace 需要 Java 起点，否则链路断裂） |
