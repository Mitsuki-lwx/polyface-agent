# tasks —— 生成管线评测集（防退化）

上游规格：`docs/spec_eval.md`　　验收：`docs/checklist_eval.md`

> 12 个任务，每个能在一次专注会话内完成。
> **最后两个（T11 接入主流程 / T12 端到端验证）是硬要求，不许跳过。**

---

## T1 · 素材规格与生成器（一次性工具）

**影响文件**：`scripts/eval/gen_corpus.py`（新）

**依赖**：无

**参考定位**：`docs/71` §5（"20~30 条固定素材 + 性质断言"）·
`docs/50` §2.1（素材长度 300~2000 字）· `python-service/app/pipeline/prompts.py`（复用 LLM 调用方式）

**做什么**：

- 定义「一条素材」的规格：长度区间、**含几个数字**、**含几个专有名词**、**含几条可核验断言**
- 按规格用 LLM 合成素材。**生成器只跑一次**，产出落盘后就冻结；
  跑分链路**不调用**生成器（见 spec §5 关键决定一）
- 生成时把「这条素材含哪些数字/专有名词」一并记录下来 —— 断言要拿它对账

**验收**：跑一次能产出符合规格的素材文件；规格里的每个特征值都能从命令行改。

---

## T2 · 冻结素材集与 manifest

**影响文件**：`eval/corpus/*.json`（新，冻结素材）· `eval/corpus/MANIFEST.json`（新）

**依赖**：T1

**做什么**：

- 把生成的素材冻结进仓库，**人工过一眼**（明显不通顺/无意义的丢掉重造）
- manifest 记录：素材集版本、条数、每条的特征计数、生成时的 prompt 指纹与模型名
- **改 manifest 等同于改测试基准** —— 这一点要写进文件头注释

**验收**：manifest 与素材文件一一对应；删掉任一条素材，跑分器能明确报错而不是静默少跑。

---

## T3 · 断言集（纯函数）

**影响文件**：`python-service/app/eval/assertions.py`（新）或 `scripts/eval/assertions.py`（新，二选一，见 T11）

**依赖**：T2

**参考定位**：`python-service/app/pipeline/generate.py:301-305`（已存在的"正文数字 vs 事实清单"比对）·
`python-service/app/schemas_gen.py`（`DraftPayload` / `QaReport` 的字段）· `platform-dna/*.yaml`

**做什么**：实现一组纯函数断言，**不调 LLM、不写文件**。至少覆盖：

| # | 断言 | 依据 |
|---|---|---|
| A1 | 正文里的数字必须在素材事实清单里有依据 | 复用 `generate.py` 已有的比对逻辑，不重写 |
| A2 | 不出现素材里没有的年份 | 防 AI 自加时间 |
| A3 | 标题非空、不重复、长度在区间内 | 平台标题机制 |
| A4 | 正文长度落在该平台区间内 | `platform-dna` 的字数约束 |
| A5 | 标签数量达标且不含 `#` | 平台标签策略 |
| A6 | `video_native` 平台必须有 `clip_sheet`，且分镜序号连续 | `docs/05` FR-52 |
| A7 | QA 报告为 passed（或失败项非空） | 现有质量门 |

**关键**：所有**阈值**都从配置/参数进来，断言函数里不写死。

**验收**：每条断言单独可调用，输入是（素材, 产物），输出是明确结论。

## T4 · 断言集的反例测试

**影响文件**：`python-service/tests/test_eval_assertions.py`（新）

**依赖**：T3

**参考定位**：`python-service/tests/test_check_scripts.py` 的写法（**每条规则都要有反例**）

**做什么**：**每条断言至少一个反例** —— 喂一个故意违规的产物，断言必须红。
另加一个"全合规产物"的正例，确认不误报。

**验收**：把任一断言的实现注释掉 → 对应测试变红（**变异测试**，见 checklist §6）。

## T5 · prompt 指纹

**影响文件**：`scripts/eval/fingerprint.py`（新）

**依赖**：无

**参考定位**：`python-service/app/pipeline/prompts.py`（6 个 system 常量）

**做什么**：对 6 个 system prompt 常量取哈希，产出稳定指纹（与文件行号无关，只与内容有关）。
写进每次跑分的报告。

**验收**：改一个字符 → 指纹变；不改 → 指纹不变（同一次跑分前后一致）。

## T6 · 跑分器骨架（矩阵 + 断点续跑）

**影响文件**：`scripts/eval/run_eval.py`（新）

**依赖**：T2、T3、T5

**做什么**：

- 遍历「素材 × 平台」矩阵，逐个跑真实生成
- **每个（素材 × 平台）跑完立即落盘** —— 中断不丢
- 重跑时**跳过已完成**的格子（除非显式要求重跑）
- 每个格子记录：产物、断言结论、耗时、token 用量、**失败归因**（断言失败 / 调用失败 / 超时 / 429）

**验收**：跑到一半 Ctrl-C → 已完成的格子仍在；再跑 → 只跑剩下的。

## T7 · 报告产出（JSON + Markdown）

**影响文件**：`scripts/eval/report.py`（新）· 产物落 `eval/reports/<时间戳>/`

**依赖**：T6

**做什么**：

- **JSON**：机器读，供 T8 做 diff
- **Markdown**：人读 —— 抬头必须写明「本报告只说明同一批输入下产出有没有变差，
  **不能**说明产品有没有用（见 `docs/50`）」
- 报告含：通过率、失败明细、prompt 指纹、模型名、耗时、token 用量

**验收**：跑完一次能拿到两个文件；Markdown 抬头有那句边界声明。

---

## T8 · 基线与退化对比

**影响文件**：`scripts/eval/run_eval.py`（扩展）

**依赖**：T7

**做什么**：与指定基线报告对比，列出：

- **退化**：上次过、这次不过的格子
- **改善**：上次不过、这次过的格子
- **不可比**：prompt 指纹或模型名不同的格子 —— **必须显式标出，不许静默比较**

**验收**：构造两份只有一处差异的报告 → 能准确指出来；prompt 指纹不同的两份 → 标为不可比。

## T9 · 成本预估与命令行可配

**影响文件**：`scripts/eval/run_eval.py`（扩展）

**依赖**：T6

**做什么**：

- `--dry-run`：只算这次要跑多少格、大约多少次 LLM 调用，**不发请求**
- 可配项：素材条数 / 素材 id 列表 / 平台集合 / 输出目录 / 复用已有结果 / 超时 / 并发

**验收**：见 checklist §2 —— **每一个可调值改了都要有可观测的行为变化**。

---

## T10 · 失败隔离

**影响文件**：`scripts/eval/run_eval.py`（扩展）

**依赖**：T6

**做什么**：单个格子失败（429 / 超时 / 网络）**不能中断整轮**，
也不能被误记成「断言失败」。报告里两者分开统计。

**验收**：人为让某一格超时 → 整轮继续；报告里它出现在"调用失败"而不是"断言失败"。

## T11 · 接入主流程（**必须有**）

**影响文件**：`scripts/eval/run_eval.py`（定稿）· `python-service/tests/`（如需）

**依赖**：T1~T10

**做什么**：

- 跑分器**调用现有生成入口**，不复制管线逻辑（spec §4）。
  先确认入口形态（`python-service/app/main.py` 的生成端点 / `pipeline/generate.py` 的函数），
  再决定断言集放哪（`app/eval/` 还是 `scripts/eval/`）
- 在 README 与 `docs/71` §5 里更新"这个缺口已补"的状态与用法

**验收**：跑分器走的是线上那条路（改一处 prompt 逻辑，跑分结果会跟着变）。

## T12 · 端到端验证（**必须有**）

**影响文件**：无（验证任务）

**依赖**：T11

**做什么**：用**真实 Key**跑一次完整矩阵（默认 5 平台 × 10 条），产出报告。

**验收**：

- 拿到 JSON + Markdown 报告，通过率是真实数字（不是 mock）
- 报告里 prompt 指纹、模型名、耗时、token 用量齐全
- 至少跑一次**变异**：故意改坏一个 prompt → 重跑 → 通过率或断言结论**确实变了**
  （这一条是整件事的意义所在：证明这个评测集**抓得住**退化）

## T13 · （后加）接入 platform-dna：把它变成「平台 DNA 的实验台」

**影响文件**：`scripts/eval/dna_rules.py`（新）· `scripts/eval/assertions.py` ·
`scripts/eval/run_eval.py` · `scripts/doctor.py` · `python-service/tests/test_dna_rules.py`（新）

**依赖**：T3、T6、T7

**为什么后加**：T1~T12 做完后才发现，跑分器**根本没读 platform-dna 的约束** ——
`body_chars_max` / `tags.count_max` / `title_chars_max` 一条都没用上。
于是「改了某平台的 DNA，产出有没有变好」这个问题答不了，而这正是
`docs/71` §5 说的 harness 该回答的事。

**做什么**：

1. `dna_rules.rules_for(platform)` —— 把 DNA 翻译成断言阈值
   （取值优先级见该模块 docstring：各平台字段名不统一，且 `0` 表示「无上限」）
2. 断言补两条：**A5 的标签上限**（平台罚的是堆砌，不是太少）、
   **A8 站外导流**（手机号/邮箱/外链/微信号 —— DNA 的 `limits.banned_direction` 明文禁止）
3. 报告加 **DNA 指纹**（每平台 + 合并）与**分平台切片**表
4. 基线可比性把 DNA 指纹也算进去
5. `doctor.py` 报平台 DNA 的新鲜度（阈值 `POLYFACE_DNA_MAX_AGE_DAYS`，非阻塞）

**验收**：见 `docs/checklist_eval.md` §4b。
