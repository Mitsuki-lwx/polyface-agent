# Polyface 项目可行性与现实推进建议

评估日期：2026-09-14  
代码基线：`master`，`a7d6650`。本次未修改业务源码、配置或数据库。

## 一、结论先行

**值得继续，但应从“全平台内容工具”收缩成“已有原创长文 → 小红书建议稿 → 人工校改”的可靠工作流。下一阶段应验证省时和复用，而不是增加功能数量。**

| 判断尺度 | 当前结论 | 原因 |
|---|---|---|
| 自用、作品展示 | 可继续 | 核心管线、工作台、存储和模板等确有实现，不只是方案文档。 |
| 面向普通创作者内测 | 有条件可行，先修核心闭环 | 质检存在误通过，事实确认和稿件编辑不足，安装和长任务体验未过关。 |
| 商业化或广泛推广 | 证据不足，暂不下“成立”的结论 | 尚未看到真实用户持续使用、省时、付费意愿的验证；技术能跑不等于有人愿意用。 |

不建议推倒重写。先保留 Java + Python + SQLite 和现有静态工作台，集中修正确性、降低使用门槛；暂不重做前端框架、不迁移 SaaS、不引入额外基础设施。

## 二、本次验证了什么

### 本轮实际执行

- 阅读关键产品文档、Python 生成/质检/LLM/观测代码，以及 Java 编排、工作台、配置和启动脚本。
- 对 `test_understand.py`、`test_generate.py`、`test_learn.py` 执行离线测试：**26 passed，1 条依赖弃用警告，测试耗时 1.94 秒**。这不是实际生成耗时。
- 在禁止真实模型调用、关闭真实配置读取的条件下，用合成响应复现四种质检边界和两种观测边界，见下文。
- 第一次网络隔离设置误拦 Windows 异步事件循环的本机通信，导致测试失败；允许内部回环通信后全部通过。这次初始失败不是项目缺陷，不用于负面评价。

### 不能混淆的证据边界

- 本轮没有调用真实 LLM、读取真实 `.env`、消耗模型额度或修改业务数据。
- 没有重跑 Java 测试、浏览器端到端测试、干净电脑安装或媒体处理测试。因此没有宣称“全项目测试通过”。
- `docs/29` 中 Java 28 项、Python 38 项及真实链路 10/10，是历史交付记录，不是本轮实测。
- 产品评审成员在首次服务失败后恢复并完成；交付评审成员因服务参数拒绝未完成，其范围由主代理直接核查。未把失败成员当成已完成的独立评审。
- 本报告不依据未经更新的竞品、模型价格或平台政策推断市场成立；市场判断限于仓库中是否存在验证证据。

## 三、决定下一步的关键发现

### 1. 功能已有积累，不能把 README 勾选情况当成真实进度

Python 已有素材理解、平台策略、成稿、规则与模型质检、失败后一次重写；Java 已有 SQLite 落库和浏览器工作台。模板、画像、复盘也有实现和测试，不是全部停在 M2。

但“已经写了功能”不代表“产品验收通过”。README 路线图滞后，部分用例验收仍未落到代码。尤其应区分模板的编辑/导出，与最终稿件的编辑/导出。

证据：`python-service/app/pipeline/generate.py:55-98,148-173,278-355`；`java-backend/src/main/java/com/polyface/backend/web/MaterialController.java:138-239`；`README.md:60-68`；`docs/07-用例模型与验收标准.md:52-79`。

### 2. “事实约束”目前不能当可靠保证——这是第一优先级

**本轮已在真实模式代码分支中替换模型响应进行离线复现；没有真实模型调用：**

| 场景 | 实际结果 | 风险 |
|---|---|---|
| 素材写每周读 10 页，正文改成 999 页；规则产生告警，模型返回通过 | 最终 `passed=true` 且 `warnings=[]` | 规则告警在真实模式中丢失。 |
| 模型返回字符串 `"false"` | 被 `bool(...)` 转成 `true` | 类型不合约可能被误判为通过。 |
| 模型返回 `passed=true`，同时有非空 `issues` | 仍然通过 | 成稿可显示“QA通过”，但问题列表仍有问题。 |
| 正文为空，标题和标签合法 | 规则质检通过 | 最基本的可交付性没有被规则守住。 |

代码根因：`generate.py:254-282` 中数字检查只产出 warning，真实模式没有合并规则 warnings；`passed` 仅依赖模型布尔转换和规则 issues，没有统一约束合并后的 issues。`schemas_gen.py:46-60` 没有正文非空约束。

另外，数字检查只比较正文与事实集里的数字集合，不验证数字对应的人物、单位、时间和语义；事实抽取本身也依赖模型，没有证据片段定位。不能把这样的“QA通过”等同于事实保证。

**建议修复标准：**严格解析模型返回结构；合并全部规则和模型问题；有阻断问题一律不得显示通过；空正文和结构异常必须拒绝；标题、正文及关键数字关系纳入校验；保留人工终审。“没有发现错误”应与“保证正确”明确区分。

### 3. 用户确认事实、编辑稿件的工作流没有闭合

- 事实清单当前展示为文本，没有增删改并保存事实集的完整入口。
- Java 生成时传递原始文本，没有传递用户确认的事实版本；Python `generate()` 再次运行理解阶段。
- 这会重复消耗一次理解调用，也让“解析时看到的事实”与“生成时使用的事实”可能不同。
- 成稿面板当前主要是预览和复制。未发现正文编辑保存、稿件 txt/md 导出或单稿手动重跑 QA 的完整实现；已有 JSON 导出属于模板，不是成稿导出。
- 历史素材接口返回的稿件列表只有摘要，但工作台直接交给需要完整 `draft/qa` 的渲染函数，未见读取 `/api/drafts/{id}` 的补齐调用。存在历史稿正文显示为空的代码路径；此项为静态证据，未做浏览器复现。

证据：`MaterialController.java:159-188,267-281`；`generate.py:317-321`；`static/index.html:347-368,443-478,775-784`。上述 Java/静态路径均在 `java-backend/src/main/` 下。

**建议：**“确认后的事实版本”作为后续生成唯一依据；补稿件正文编辑、保存、重新质检和导出；历史查看读取完整稿件。对普通创作者而言，这些比新增模板种类更重要。

### 4. 长任务和发布承诺不匹配

- Java 调 Python 的读取超时固定为 **180 秒**：`PythonClient.java:28-35`。
- 最新文档记录单次真实小红书生成 **250 秒、多次 429、最终 QA 未通过（2 issues）**：`docs/34-平台DNA调研-交付说明.md:68-82`。
- 较早记录是 101 秒；默认已改串行，文档预估五平台可能超过十分钟。后者是历史预估，不是本轮测量：`docs/29:25-29,54-63,87-91`。
- 当前 Java 等到 Python 全部结果返回后才逐稿落库；Python 串行阶段异常直接向上抛出，存在后续平台失败而前面产物未交付的路径：`MaterialController.java:188-227`；`generate.py:340-355`。

这意味着：即使 Python 最后能生成，前端链路也可能先超时。**250 秒记录不能直接证明本轮用户界面已超时，但足以证明设计预算存在冲突。**

建议默认单平台；复用事实解析；明确任务级耗时/调用预算、阶段进度、失败可重试和已完成结果保留。如果单平台仍稳定超过请求预算，再做轻量后台任务与状态查询；不需要立刻上分布式任务平台，也不应只无限延长超时。

### 5. “下载即用”和“数据不出本机”都需要收回到真实边界

**交付：**`scripts/start.bat:7-14` 依赖预先存在的 Python venv 和 Maven，包含开发机路径 `D:\apache-maven-3.9.11`，固定等十秒再开健康页；README 写 Java 17+，`pom.xml:20-22` 实际目标是 Java 21。当前不能当成已验证的普通用户安装包。

**隐私：**本地存储不等于本地推理。真实调用会把提示词与相关素材发往用户配置的模型供应商，代码见 `python-service/app/llm.py:145-162`。README 的“数据不出本机”以及 `docs/06:119` 的“不经过第三方服务器”不成立。可选观测的数据范围也应单独披露。

**本机访问：**Java `application.yml:1-2` 只设端口，没有显式本机地址；Python `main.py:36-42` 放行任意来源。没有证明当前机器已对外暴露，因为启动参数和防火墙可影响实际结果；但发布默认配置应收紧，并在干净环境检查实际监听。不要把“页面在 localhost 打开”当成访问控制。

建议先做有依赖说明和检查的内测启动包，不必一步到位制作安装器；公开宣传需在干净环境验收后再称“下载即用”。

### 6. 工程通过、真实稿件质量、用户价值是三种不同结论

最新 DNA 改造只做了提示词对照和一次真实生成；提示词变长 47%、mock 测试通过，都不能证明改稿更省时。仓库未见真实作者的持续使用、编辑耗时、盲评对照或付费验证。

`docs/06:15,73-87` 自己也注明需要种子用户验证、付费意愿未验证。现阶段不宜继续把原可行性报告的“市场空位”“成本可忽略”当成结论。总成本还包括安装支持、人工校稿、重试和规则维护。

## 四、现实推进路线：先达标，再扩范围

### 第一关：修到不误导用户

优先处理质检误通过、规则告警丢失、空稿件、事实版本未复用、历史正文读取问题；修正隐私与环境要求的文字承诺，收紧默认监听和来源。

验收建议：建立至少 20 个确定性回归场景，覆盖新增数字、数字关系改变、空正文、模型布尔类型错误、问题列表非空、格式异常、超时和失败。要求这些已知错误不再被标为通过。这个“20”是建议的初期覆盖量，不是充分证明真实模型可靠。

### 第二关：形成可交给一个人的完整内测版

只开放一个主流程：

**粘贴原创文本 → 核对并保存事实 → 生成小红书稿 → 编辑并保存 → 查看风险提示 → 复制/导出。**

复用现有架构，补完整历史、明确真实/mock模式和失败提示；给调用设置预算，保留可恢复状态。制作最小启动包并验证缺依赖、端口冲突、中文/空格路径、关闭后重启及历史数据保留。不先追求安装器、自动更新和跨系统打包。

### 第三关：用真实作者验证它是否值得存在

建议找 **5 位每周已有原创长文、正在手动改小红书稿的作者**，首轮每人 2 份真实素材，共 10 组。比较 Polyface 与作者惯用的“聊天 AI + 提示词”，尽量控制模型和素材，随机隐藏来源顺序。记录：

- 人工编辑时间；模型等待时间和端到端总时间分开记录。
- 重大事实错误、稿件可发布率及模型实际用量。
- 是否再次主动带新素材使用；安装和求助成本。

**建议的早期过线门槛（不是现有结果，也不构成统计显著证明）：**

1. 人工编辑时间中位数下降至少 30%，且不能用少编辑掩盖无法接受的长等待。
2. 至少 8/10 稿能在 10 分钟人工修改内达到作者愿意发布的程度。
3. 这批样本中重大事实捏造为零；仍不代表系统保证永不出错。
4. 第二周至少 3/5 人主动带新素材复用。

未通过：针对最大失败原因修一轮后再测，不通过就继续收缩定位，或把它保留为自用/作品项目。连续两轮没有明显价值，不再扩平台。通过后才增加公众号这一第二场景，再讨论商业化。

## 五、现在应暂缓什么

- 五平台并行打磨、海外平台扩张。
- 自动成片等远期多媒体方向。
- 新一轮模板学习、复杂效果归因或“越用越懂你”的扩展。
- 新的观测平台工程、前端框架重写、SaaS化、收费系统。

已实现代码可以保留，不必删除；只是从下一阶段的主验收目标中移出。

## 六、补充技术风险：观测不能改变业务

本轮用替身观测客户端离线复现：`trace_span` 包裹的业务代码抛出模拟限流错误时，实际变成 `RuntimeError: generator didn't stop after throw()`，随后被分类为普通 `LLMError`。根因是上下文管理器在捕获 `yield` 内异常后再次 `yield`：`python-service/app/observability.py:109-122`。这会破坏预期的限流重试语义；不代表历史 250 秒故障一定由它造成。

另一个边界是 `flush():125-132` 未先判断启用开关，生成接口无条件调用它（`main.py:104`）；离线替换 `_get_client` 证明“关闭时仍调用初始化入口”，但未向真实观测服务发请求。需补“开关关闭绝不初始化”和“观测故障不替换业务异常”的回归测试。

## 最后建议

**下一张开发任务应是“修质检和事实确认闭环”，不是“再加一个功能”。**随后交付最小内测版，用真实素材证明它比作者现有方法更省事。这个项目的机会在可靠工作流，而不在功能清单长度。
